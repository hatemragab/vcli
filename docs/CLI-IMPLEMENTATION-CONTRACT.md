# Authorized CLI implementation contract

The owner authorized the full documented CLI scope on 16 November 2026 after the native reference review. Work uses the existing checkout, no new worktree, private/local distribution and no publication/provisioning/deployment. Hatem owns release decisions; contributors own patch evidence. Exact npm namespace/license selection remains required before public distribution. `@vcli/cli` versions 0.1.0/0.1.1 are private local identities, not registry ownership claims.

## Baseline

Reuse tested Node 26.13.1, npm 11.20.0, ESM, TypeScript 6.0.3, native Node tests, Commander 15.0.0, Zod 4.6.7, ESLint 10.15.0 and Prettier 3.10.1. Generated NestJS uses the verified reference pins. npm replaces the unverified pnpm recommendation for this implementation. Prefer public packages at useful boundaries; do not invent a CLI parser, compiler, templating framework or supervisor.

Use flat NestJS entity/service/module files and optional controllers/helpers, one class per file, typed inherited native BaseRepository, standard build/start, explicit injection and validated boundary inputs. Never emit circular imports/feature dependencies, forwardRef, global locator/module shortcuts or hidden loading. Database is optional for the minimal foundation; when selected, exactly one MongoDB or PostgreSQL implementation and its dependency closure is emitted. No runtime DB switch, universal filter adapter or app memory database.

## Shared interfaces and ownership

`src/contracts.ts` is the initial shared contract. Engine owns `src/engine/**`, can refine contracts after notifying recipes/coordinator, and owns `test/engine*.test.ts`. Recipes owns `src/recipes/**`, `templates/**`, `test/recipes*.test.ts`, and documentation `docs/CLI-RECIPES.md`. It consumes the contract and announces its catalog export promptly. Coordinator owns root package/lock/install/build/config, CLI entry/commands, integration tests, parent docs/phase status and all final generated-output acceptance. Existing references are read-only source material to these workers.

Desired state is `vcli.json` ProjectConfig; `vcli.lock.json` records realized recipes/options, ownership hashes and separate source/install/check outcomes. Capabilities are keyed by family, each `{recipe,options}`. Foundation is always explicit/selected. Database/auth/mail/storage/realtime/diagnostics/deployment are exclusive per family; independent purpose families permit FCM plus APNs. Required families must be selected explicitly: resolver never chooses an arbitrary provider. Capture can be selected for local auth; Firebase sign-in itself must not require SMTP or a second JWT pair.

RecipeCatalog metadata is pure: versioned IDs, family requirements, conflicts and validated options. Its async render returns a complete deterministic desired file set, checks, warnings and external/manual pending work. The renderer is trusted bundled code, not a public plugin runtime. Recipe IDs and exact options are frozen by worker announcement before command integration. Tool-owned composition/config files may be regenerated; developer scaffold files are created once and never rewritten on add. Existing package custom scripts/dependencies and unmarked docs need bounded managed treatment, not wholesale replacement. Changes to exclusive installed providers require an explicit supported migration and are rejected by ordinary add.

## Engine requirements

Provide typed public functions for init/add/generation plan, saved-plan application, inspection/doctor/recovery. Announce signatures early. Pure preview creates no file/directory/lock and runs no package manager/provider. Plans include touched expected-absence/hash preconditions, recipes/versions and source/install/check/manual outcomes. Stable JSON command output excludes raw file contents/secrets. Saved plans/journals are explicit private local writes. No raw environment/provider credentials enter config, plans or output.

Reject unsafe identifiers, traversal, symlink ancestors/targets, incompatible toolchains, desired/realized drift and managed/dependency conflicts. Recheck under an exclusive project operation lock immediately before mutation. Use argument-vector process execution, no shell interpolations. Journals distinguish completed source, install pending/failed and checks pending/failed. Recovery restores only bytes matching an operation post-image and preserves subsequent user edits. Tests must meaningfully prove interruption/stale plans/concurrency/install failure/recovery, not snapshot implementations.

## Execution constraints

Worker source tasks default to scoped checks and isolated fixture emission. An explicit coordinator dispatch may assign task-owned local installs, capped services or Playwright acceptance within the host/download rules; it never grants unrelated provisioning, publication or live provider/deployment authority. Shared root distribution builds remain coordinator-owned. Scoped worker-owned isolated fixture emission and finally-cleaned in-process loopback protocol peers are allowed for focused tests; shared root/generated-app builds and real DB/service orchestration stay with the coordinator. Existing installed tools may run scoped noEmit/lint and tests. Coordinator owns root dependency setup and final evidence; explicitly assigned local acceptance may be delegated with finite process/resource ownership and exact cleanup. Reuse caches; ask only if a new download batch exceeds 500 MB or an actual missing privileged/external action requires it. Nonzero checks are failures to fix/report, not completion. All workers must use the orchestration ask/worker_done lifecycle and report exact files/commands/evidence limits.

The selected logging event schema is managed technical output because its database/capability allowlists change on add. The injectable logger implementation remains scaffold-owned. Private0.1.1 adds peer-free auth runtime version identity, the finite maintenance edge and selected HTTP mail; source/install/check/provider outcomes remain separate.
