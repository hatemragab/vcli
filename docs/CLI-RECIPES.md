# Curated CLI recipes

The private local CLI exports `recipeCatalog` and `renderScaffold` from `src/recipes/index.ts`. Rendering is asynchronous, deterministic and read-only: it returns complete desired files, scoped check commands, warnings and explicit manual/external work. The engine resolves requirements and applies ownership/preconditions; rendering validates the explicit selection again. No provider is selected implicitly and ordinary add cannot replace an exclusive installed provider.

Bundled trusted assets under `templates/runtime/` are package contents. Generation reads them relative to the installed module, never from repository examples or absolute contributor paths. Both native variants are included as CLI tooling; only the selected variant is emitted to application source and dependency declarations. Generated apps pin the private coordinated CLI through `@vcli/cli: file:tools/vcli`; the coordinator bundles that local CLI distribution. This is not a registry ownership or publication claim.

Firebase defaults to all four `email-password`, `phone`, `google`, `apple` methods and `actionDelivery:'provider'`. A nonempty distinct subset is allowed. Provider mode uses the client SDK and needs neither application mail nor local JWT. Application verification/reset links require selected reliable mail and the server-controlled continue/Hosting/mobile policy. Local auth uses a private bounded JWT key ring and the narrow optional-peer auth runtime. See [identity](CLI-IDENTITY.md) and [mail](CLI-MAIL.md).

Local auth defaults to the existing email/password profile. Select `--auth local --local-identifier username` or `auth.local` options `{ "identifier": "username" }` for mail-free username/password authentication. Interactive init offers this mode explicitly and never selects capture for it. Username accounts have no email or verified-email claim; verification and forgotten-password reset routes, action-token services and mail contracts are omitted. Authenticated current-password change, JWT/refresh sessions, installation possession and account/session lifecycle remain available. The preserving identity schema retains its established inactive action storage, without selecting a mail transport. Ordinary add refuses switching an installed project's identifier mode. See [the username contract](CLI-USERNAME-AUTH.md).

Diagnostics defaults to application evidence with MCP/Vector/Logdy/testCapture disabled and `reader:'local-same-user'`. Optional sources are workers, database, infrastructure and tests; database requires the selected native DB, and test capture requires tests. Restricted remote reads use an explicit private scoped profile. Isolated/shared-production diagnostics, arbitrary custom S3, native-ws cluster, durable realtime replay and queued push dispatch are unsupported; selection rejects unsupported options before mutation.

A minimal selection has only `foundation.nest`. It emits ordinary Nest build/start/watch scripts, explicit health initialization/shutdown state, selected environment validation/examples, redacted structured logging and safe HTTP errors. It contains no database, authentication or provider SDK. Every selected family adds its own imports, dependencies, environment keys, runtime composition, assets and guidance. Application dependencies are pinned from reviewed reference versions using only actual emitted imports; unmapped imports fail rendering. No application package lock is invented: package installation and closure verification are coordinator acceptance steps.

Configuration validation, example files and deployment environment keys use one selected field model. Required credentials are blank examples. `APP_ENV_FILE` loads only an explicitly selected private file with process environment precedence, and a production invocation rejects a development/test-named file. Runtime provider-selector variables are rejected because source selection is fixed. Local JWT key rings are required in development as well as production; the renderer never commits a usable key.

Owner account/identity/session persistence, refresh atomicity, private-media state transitions, push fencing and protocol cleanup are selectively bundled from the reviewed native runtime. The generated root composes selected configured modules explicitly. Each provider module exports its injectable service; root sibling imports do not establish visibility for a custom consumer. Database initialization imports only selected owner schemas and ships the PostgreSQL SQL asset when needed. Media/push schema initialization is explicit and application startup does not create their schemas.

The explicit `example.notes` recipe provides the reviewed owned REST example and advisory hints; `--preset api` includes it, while minimal remains empty. Name-only scaffolds still expose no operations. Realtime consumers recover authoritative state through owner REST reads. Owner persistence classes and business helpers are scaffold-owned; additions preserve their bytes. Tool-owned composition, provider selection modules, configuration, selected operation artifacts and bounded guidance/package fields are managed. README and AGENTS managed text is enclosed by `<!-- vcli:managed:start -->` and `<!-- vcli:managed:end -->`; the engine preserves prose outside those markers and unknown package keys. `AppCustomModule` is developer-owned. Its stable register method receives explicit named configured module handles from generated composition; a data scaffold module accepts the database module handle through its own register method. For example, AppCustomModule.register can import ProjectItemModule.register(capabilities.database!) without editing generated composition. Unused handles grant no implicit Nest provider visibility. Copied runtime security updates need a reviewed manual patch or a narrowly approved codemod when source has been customized.

`renderScaffold(config, {kind, name})` supports `feature`, `service`, `controller`, `dto`, `repository`, `command`, `query` and `realtime`. Names are bounded kebab-case identifiers and cannot collide with built-in owner modules. Files are scaffold-owned and include explicit integration instructions. A database feature or repository uses its selected native `BaseRepository` and schema, with schema initialization/migration left explicit. Controllers contain no routes, commands/queries throw a named unfinished-operation error, and DTOs start with an empty strict schema. Realtime scaffolds delegate typed publication to the selected service and require explicit consumer-module imports and trusted ownership policy. No arbitrary consumer source is rewritten.

Implemented runtime contracts are documented separately: [identity](CLI-IDENTITY.md), [mail](CLI-MAIL.md), [push](CLI-PUSH.md), [storage/media](CLI-STORAGE.md), [notes](CLI-NOTES.md), [realtime](CLI-REALTIME.md), [diagnostics](CLI-DIAGNOSTICS.md), [operations](CLI-OPERATIONS.md), [release/restore](CLI-RELEASE.md), [native deployment operators](CLI-DEPLOYMENT-OPERATORS.md) and [maintenance](CLI-MAINTENANCE.md). This catalog describes source support; exact local, synthetic and real-service evidence is recorded in those contracts and [CLI verification](CLI-VERIFICATION.md).

External Firebase client methods/action links, SMTP/domain/inbox, Resend, FCM/APNs/device behavior, AWS/R2 and all live target/TLS/persistence profiles remain separate pending resources. Source or controlled protocol tests do not establish their acceptance. Deployment cluster support rejects private local storage/evidence roots; external shared DB and the selected realtime engine/adapter must meet the explicit profile. Durable mail is implemented with encrypted native intents; push remains an immediate fenced operation.

Every generated app has architecture and fixed-database isolation checks wired into check and prebuild. The checks include type-only import cycles, feature direction, one class per file, forbidden loading shortcuts and declared/locked opposite-database closure; the foundation gate rejects either database implementation.

Scoped tests assert actual selected file/import/dependency sets, four authentication/database outputs, deterministic repeat rendering, schema assets, scaffolding and absence of repository-only runtime references. Opt-in `recipes-compilation.test.ts` uses separately installed SDK directories via `VCLI_RECIPE_MONGODB_NODE_MODULES` and `VCLI_RECIPE_POSTGRES_NODE_MODULES` for actual TypeScript noEmit, ESLint and architecture fixtures. Eight profiles cover minimal and capture-only apps, both auth/database combinations, local/Socket.IO and R2/Centrifugo; the fixtures never install or start services. Import/syntax assertions and noEmit compilation are static evidence. Generated tarball install/build/boot, real persistence, provider, device and deployed evidence remain separate coordinator gates.
