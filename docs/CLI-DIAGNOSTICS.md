# Diagnostic runtime integration

Worker D owns the common core logging/diagnostics, diagnostic module, diagnostic-only scripts and `ops/diagnostics` templates. Generator/config/catalog/composition and generic process/test launch remain root-owned. This document separates the initial source/protocol checks from the current-source native service gate below. Packed application, real native database and deployed evidence remain separately attributed; no production isolation claim is made.

## Selected source contract

Root emits `src/core/diagnostics/source-contracts.ts` whenever diagnostics is selected, plus the selected producer classes and diagnostic module helpers. Existing `AppLoggerService.record`, `runWithContext`, `status` and `flush` remain compatible. It still validates facts before stdout and retention; terminal HTTP accounting is unchanged. No module or core file imports a feature.

`SourceEvidenceService.open(config, environment, sources)` composes independent `DiagnosticsService` writers. Pass that returned service as the logger's existing optional sink. `sources` is a nonempty distinct subset of `application`, `workers`, `database`, `infrastructure`, `tests`; emit and select only actual configured producers. `config` has `directory`, `maxBytes` (512–10485760), `maxFiles` (1–10), optional `maxAgeMs` (1000–604800000). Application files remain at the original root; other sources use the fixed `workers/`, `database/`, `infrastructure/`, `tests/` children. Directories are 0700, files and writer locks 0600. No caller can query arbitrary paths. Independent budgets default to 1MiB ×3 per selected source; the maximum selected total must be reviewed when changing those limits. Age expiry is enforced on queries; old files are removed on writer open/rotation, so stopped writers do not promise timed disk cleanup. Stale writer locks fail unavailable; an operator must verify the former writer has exited before removing its exact lock.

`DiagnosticReaderService(config, environment, {sources, grant?})` reads those designated paths with `O_NOFOLLOW`, bounded snapshots/pages and signed query/environment/grant/source-scoped cursors. Cursor keys are process-local; reader restart expires earlier cursors. Source coverage lists observed parse counts/ranges, unavailable sources, malformed/expired/overflow observations, and unmeasured loss. A configured source directory is evidence availability, not proof a live producer or viewer is connected. Empty results never prove absence. `source.status` is emitted by `SourceEvidenceService.flush`, containing bounded cumulative `dropped`/`malformed` observations; crash loss remains explicitly unknown. No viewer acknowledgement is inferred.

`close()` performs a final source-status flush before closing its owned writers. Reader snapshots stream at most 128 directory entries per source. A page scans at most 2MiB, emits at most 100 records and 192KiB of event JSON, and carries a cursor of at most 16384 bytes. Application/source lines remain limited to 2048 bytes; selected test-result lines may use 4096 bytes. Reports that cannot fit the configured per-file bound are dropped and flush reports incomplete collection. Polluted directories and unsafe source roots fail bounded.

Invalid source selections fail validation before path access. Source-directory I/O failures return unavailable destinations without touching unsafe children, preserving independent stdout and business callback outcomes. Root can report `status()`/failed `flush()`; optional retention failure is not a business retry trigger. `SourceEvidenceService` is a separately composed sink, not a subclass of `DiagnosticsService`; root's generated module registration must accept/register that selected sink instead of assuming the former concrete writer type.

Core producers depend only on the existing logger, with normal explicit construction at the composition root:

## Assertion capture contribution

Emit `test-evidence.service.ts` and `test-result-schema.ts` for selected test capture. Root's ordinary test wrapper constructs `TestEvidenceService(sink)` and calls `capture({runId,operationId}, execute, {flush,stopOwned,deadlineMs})`. `execute` returns `{assertions,artifacts}` from real assertions. Each assertion has a finite check (`exit-code`, `http-status`, `persistence`, `authorization`, `redaction`, `protocol`, `invariant`, `custom`), ordinal, outcome and finite code. Maximum 8 assertions and 4 artifacts; artifact metadata is kind, byte count and SHA256 only, never a path, URL, body or arbitrary failure text. No artifact bytes are collected. The root wrapper must sanitize any external artifact before hashing and retain it under its own declared access/expiry policy.

Assertion failure remains `failed` even if log collection is incomplete. Exceptions become a sanitized failed assertion; invalid/no assertion reports are `aborted`. Cleanup and flush each have an independent 10–5000ms deadline (default 1000). The result records `logsComplete` and `cleanupComplete`; a final bounded flush returns `resultRetained` to the runner separately. Root must preserve nonzero assertion outcomes and report incomplete retention separately. Hooks may stop only handles the root wrapper created; no port scanning, PID discovery or process-name killing. Timing out a hook does not forcibly cancel it; root's process owner must implement cancellation/exit cleanup. No test execution hook is reachable from MCP.

`tests.getResult({runId,operationId,cursor?})` returns retained `test.result` records plus the same coverage, cursors, expiry/gap and truncation semantics as logs. No result means unavailable/expired evidence, never a passed test. `DiagnosticReader` now includes `getTestResult(input)`; MCP accepts this small read-only interface, with explicit Nest injection token `DiagnosticReaderService` preserved.

Reports also accept optional `revision` (40/64 lowercase hex), `dirty` (boolean), `capabilities` (up to 16 finite recipe IDs) and `versions` (finite `node`, `database`, `vector`, `logdy` fields containing numeric three-part versions). The root runner supplies observed values; missing metadata stays missing rather than becoming invented evidence. No raw config/environment/package output is retained. Unknown nested artifact/report fields are removed. A `passed` result must have an actual passed assertion and no failed assertions; a `failed` result must include a failed assertion.

## Access and restricted remote selection

Same-user local stdio is explicitly **not a sandbox**. Root may select the implemented `restricted-remote-read` profile, with a separately supplied private JSON profile; it must continue rejecting isolated/shared-production modes until actual OS, credential and network enforcement exists. The remote profile is a transport/application authorization boundary, not a general filesystem or OS sandbox.

`DiagnosticGrant` is strict `{project:<generated project>, environment:'development'|'test'|'production', runs:[{runId:<UUID>,operationIds:[<UUID>]}]}` with at most 32 runs and 64 operations per run. A remote reader must request an allowed run; every returned event must have an allowed operation. Cross-project/environment/run/operation/cursor requests are denied. Local readers without a grant intentionally trust the same user with all designated retained evidence. Scoped status suppresses aggregate file/byte counts.

`RemoteDiagnosticReader(profile)` validates strict `{profile:'restricted-remote-read',endpoint,readToken,grant,timeoutMs?}`. Endpoint is one canonical URL with a literal IP, exact `/v1/diagnostics/query` path, no credentials/query/fragment; HTTPS uses normal certificate verification, and HTTP is allowed only for literal 127.0.0.1/::1. Domain names, proxies, redirects and arbitrary egress are unsupported. Tokens are explicit dedicated base64url, 43–128 characters; no dotenv, application SDK, operator credential, default token or environment inheritance. Timeout 50–5000ms (default 2000), at most 2 active requests, bounded response 256KiB. Disconnect, denial, malformed/oversized response and unavailable backend have safe finite errors. A literal HTTPS address needs a valid certificate for that IP; domain-based production routing is deliberately not advertised.

`new RemoteDiagnosticServer(reader,readToken,grant).createHttpServer()` returns an ordinary HTTP server for root-owned binding/TLS/process setup. Root must give it a `DiagnosticReaderService` configured with **the same grant** and selected sources. Only exact POST `/v1/diagnostics/query` exists; body is `{project,environment,tool,input}`. All six finite tools share `diagnostic-query.ts`: `project.describe`, `capabilities.list`, `diagnostics.status`, `logs.search`, `operations.timeline`, `tests.getResult`. No shell, SQL, Docker, paths, code, generation, execution or deployment methods exist. Requests are bounded, authenticated, authorized and revalidated before response; return only sanitized data. Remote credentials must be issued separately, with read-only scope and an independently configured destination; never reuse deployment/provider tokens.

Root owns selected recipe options/config/env registration. Suggested options are `sources`, `testCapture` and `reader:'local-same-user'|'restricted-remote-read'`, preserving existing `mcp/vector/logdy` booleans; validation must reject a database source without the selected native database and reject stronger isolation claims. Root can map `EVIDENCE_MAX_AGE_MS` and selected `EVIDENCE_SOURCES` into the APIs above; no runtime DB selector is added. No additional npm dependency is needed beyond already selected Nest, Zod, Pino and the optional MCP SDK.
