# Selected push lifecycle

The push recipes emit directly injectable `PushService` with only the selected FCM/APNs implementation and one native owner store. This source slice covers P05-T05–T09 and prepares the push portion of T10/A01/A05–A08/A10/A11. It does not close Phase 05, the generated identity/native/HTTP entry gate, packed installation/custom-add, real-provider or physical-device acceptance. The hand-built reference applications are unchanged and their evidence remains separate.

## Integration contract

`src/recipes/render-push.ts` owns selected push output. Native-independent files moved to `templates/runtime/common/src/modules/push/`: entity, service, repository, transitions, storage mapping, controller, state-store contract, validation, retry-after and `trusted-call-invitation-policy.ts`. FCM contributes `fcm-push.service.ts` and `fcm-credentials.ts`; APNs contributes `apns-push.service.ts`, `apns-payload.ts` and `apns-transport.ts`. MongoDB contributes only `templates/runtime/mongodb/src/modules/push/mongo-push-state-store.ts`; PostgreSQL contributes only `templates/runtime/postgres/src/modules/push/postgres-push-state-store.ts`. No dual driver selector, production memory store, foreign identity model or cycle is introduced.

The generated module keeps `initializePushSchema(config)` and `createPushRuntime(config,authority)` compatible. The latter accepts optional third argument `dependencies: Pick<PushRuntimeOptions,'voipPolicy'> = {}`. Module factories explicitly compose/export PushService and import the neutral HttpSecurityModule registered with the supplied PrincipalAuthority. The repository takes its selected native state store. PushService retains its first six constructor arguments `(destinations,senders,authority,wait,routes,scope)` and accepts a seventh `PushRuntimeOptions` with environment, trusted voipPolicy and a test clock. Production factory supplies the configured environment and optional policy, never a replacement authority or test sender. Provider constructors have explicit controlled-test seams; environment configuration cannot select an arbitrary APNs endpoint.

Config integration reads these exact fields:

| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

FCM credentials use bounded <=64 KiB reads, regular-file/no-follow/private mode checks, service-account shape and matching project. APNs uses bounded <=16 KiB private/no-follow PKCS8 ES256 key reads. Invalid files produce fixed safe errors without source content/path. Firebase Admin uses a separately named messaging app; local JWT+FCM requires no Firebase identity selection. ADC is an explicit operator choice and may use shared platform infrastructure; the identity credential file is never read by push. SDK/package pin integration stays coordinator-owned.

Assets are `clients/push-client.mjs`, neutral `ops/push/README.md`, selected `ops/push/fcm-device-checklist.md` and/or `ops/push/apns-device-checklist.md` plus `ops/push/callkit-example.swift` for APNs. They describe actual registration/rotation/revoke, platform capabilities, incoming-call authorization and immediate PushKit/CallKit reporting. The Swift example is an application integration example, not a compiled native app or a completed calls product. No generated secrets or contributor paths are used.

## Persistence, ownership and migration

Each destination persists account/session/installation IDs, exact positive installationGeneration, independent UUID token generation (`generation`), app scope, environment, provider, purpose, platform, restricted token/hash and update time. Server registration ignores caller ID/generation/hash as ownership inputs; it derives authority and generates secret/token identity itself. Re-registering within the same binding/purpose preserves ID and rotates token generation. Newer binding generations replace stale rows for that installation/scope/environment; stale writes cannot overwrite an observed newer generation. Foreign installations cannot steal a reserved token. Token uniqueness includes provider, scope and environment, and forbids duplicate-purpose claims of the same token.

The bounded aggregate remains at most 1024 globally and 32 per account. MongoDB revision CAS (16 attempts) and PostgreSQL `FOR UPDATE` transaction serialize owner invariants and exact removal. Providers are never called from these retryable/transaction callbacks. No new SQL migration asset is required: the selected initializer still explicitly creates the native aggregate collection/table, and startup checks existence without migration. Native writes decode/validate their complete next state before persistence.

Legacy records lacking installationGeneration or explicit environment decode as generation zero. Zero is never eligible for list/send/removal via an authenticated positive generation. Registration can replace a legacy row for that owned installation/scope; there is no automatic owner-preserving migration or generation inference. Have authenticated clients re-register. Legacy rows on other installations remain token reservations until explicit operator ownership review/removal; this deliberately prefers a conflict over stealing a token. Backups and DB access carry raw destination secrecy obligations.

Every register/list/remove/self-send checks current PrincipalAuthority account, session, installation, exact positive generation and expiry. List/remove are installation-scoped and return no account/session/token/hash. Registration checks again after its write: a session/rebind race may leave only a fenced old-generation row, never make it eligible for a replacement owner. Safe HTTP register/list summaries include id, installationId, installationGeneration, token generation, provider/purpose/platform, environment and updatedAt; OpenAPI documents those fields. Removal requires destination ID and exact token generation. Logout/revoke of the registering session fences its destination; a still-valid sibling session re-registers when needed. Rebind/possession rotation invalidates the old installation generation. Safe list/revoke cannot use a client installation ID as possession proof.

## Dispatch and provider outcomes

Trusted `notifyAccount` and `notifyInstallation` accept UUID operationId, purpose, small validated opaque data references and <=five-minute expiry. Public `notifySelf` additionally rechecks the initiating session and pins its installation generation; HTTP accepts ordinary/background only. Payload byte count, string/key count/length, reserved keys and purpose-specific alert rules apply to programmatic callers too. Input is cloned before async work.

Ordinary routes to FCM when selected, otherwise APNs. Background and VoIP use APNs only. FCM ordinary and direct APNs VoIP coexist without double ordinary delivery. APNs alert uses base topic/priority10, background base topic/priority5/content-available with no alert, and VoIP `.voip` topic/priority10/expiration0. The origin is fixed to the correct Apple production or sandbox endpoint with verified TLS. Provider outcomes are per destination: accepted reference, permanent/configuration/payload rejection (without pruning), explicit invalid token, unavailable/throttle with retry-after, or unknown possible acceptance.

FCM invalid-registration-token/not-registered can authorize exact cleanup; invalid-argument, credentials/APNs authentication and generic payload failures cannot. Unknown SDK/network errors remain unknown. Missing exposed FCM retry headers use a conservative one-minute delay; headers that are exposed are parsed without shortening. The Admin SDK may retry some underlying transport failures internally. APNs 429/5xx preserve retry-after; credential/topic/environment/payload failures do not prune. APNs Unregistered requires status410 plus a finite provider timestamp >= that registration's updatedAt. BadDeviceToken/DeviceTokenNotForTopic remain non-pruning configuration rejections because misconfiguration can cause them.

Dispatch is immediate and bounded: four operations, serial per destination, at most32 destinations per operation and three attempts. Waits are at least1s then2s, honor longer retry-after and refuse waits >=expiry. A backoff >2s is returned without sleeping/scheduling, so the caller sees pending unavailability honestly. No scheduler, queue, durable deduplication or exactly-once promise is added. Unknown never retries automatically. FCM timeout leaves the pending SDK call counted until settlement, limiting overlap; APNs closes the HTTP2 client at completion/timeout. Raw SDK errors do not enter public outcomes.

The service rechecks the exact persisted binding/token and current session generation before submit. Production FCM also invokes a final authority callback immediately before SDK send and prevents a timed-out callback from starting a later send; APNs invokes it after connecting/signing and before opening the token-bearing request stream. The final callback rechecks expiry, initiating self authority when present, call policy for VoIP, persisted token and current authority. Delayed invalid-token cleanup rechecks eligibility and conditionally removes only that exact account/session/installation/binding/token generation. Rotation/rebind protects its replacement.

A concurrent authority change after the final check, SDK-internal transport retries, bytes already in flight and provider-accepted notifications cannot be recalled. Token disclosure on an existing connection begins at the APNs request path/SDK send. Keep confidential data out of pushes and require current authenticated application reads. Provider receipt establishes neither OS presentation nor a valid/accepted call.

## Trusted incoming-call seam

VoIP is supported programmatically only when composition installs TrustedCallInvitationPolicy. Its `authorize` receives accountId, installationId, installationGeneration, callId, operationId, expiresAt and now, and runs for each destination/attempt and at final disclosure. Implement it above call/push owners using a deliberate current-call service: read the actual ringing invitation, verify recipient membership, intended installation binding, operation identity and expiry, and deny completed/cancelled/foreign calls. Return false/throw to fail closed. Never authorize on UUID syntax alone or import call raw models into push.

Default composition has no policy and returns `VOIP_POLICY_NOT_CONFIGURED`. Denied current invitations return `VOIP_CALL_NOT_AUTHORIZED`; there is no public arbitrary self VoIP endpoint. Registration/list/revoke of VoIP destinations remain safe and supported while policy is unconfigured. A real Apple call flow still needs application-owned call facts, PushKit credentials/delegate lifecycle, immediate CallKit reporting, completion and physical-device evidence.
