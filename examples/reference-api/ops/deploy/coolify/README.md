# Coolify: prebuilt image + Compose, one API instance

This artifact uses Coolify's documented Git-based Docker Compose application path. Record the actual Coolify version and validate the Compose/environment/health interpretation on an authorized test target. Artifact presence is not deployment evidence; no Coolify API operator is implemented.

1. Publish an authorized reviewed image separately; set `REFERENCE_IMAGE` to its digest in Coolify. Select this Compose file as the application configuration. For the Raw Compose mode, explicitly configure native ingress/networking according to that installed version; do not assume the normal mode's automatic labels apply.
2. Enter private runtime variables through Coolify, never Git/build args. The example concretely selects local storage and Socket.IO and declares external database and SMTP. Set private authenticated MongoDB `DATABASE_URL` with replica-set transactions. This image has one native database implementation. Local auth needs `JWT_SECRET`; Firebase auth additionally needs runtime ADC credentials and reviewed method allowlist. The full root schema governs conditional requirements. For S3, push, ws or Centrifugo selections, review and add their actual variables/service contracts before changing the profile; they are not auto-provisioned here.
3. Precreate stable private external volumes named `reference-api-uploads`/`reference-api-evidence`; prepare and verify both mounted roots with mode 0700 and UID/GID 1000 ownership before starting the API. Preserve existing contents; image directory permissions do not repair mounted volumes, and the app does not change their ownership automatically. Map a native HTTPS domain to service `api`:3100. Keep database, diagnostic and Centrifugo callback/internal APIs private. Permit WebSocket upgrades for the chosen endpoint.
4. After the image build, run `node scripts/migrate.ts` from `/app` as a single release job using the exact image and injected environment before replacing the API. It initializes identity, media, push and notes; the identity-only command is insufficient. Follow the [common release procedure and setup limits](../../../docs/operations.md#image-deployment-and-release). A failed or uncertain setup stops the release until all owner schemas are inspected/reconciled before any retry; do not run release setup on every API boot. The Dockerfile's readiness healthcheck travels with the image; Compose-based resources use their image/Compose healthchecks, not an unrelated application healthcheck page.
5. Deploy through Coolify and record liveness/readiness, real login/note persistence/realtime/revocation, exact image and volume identity, and persisted upload reads after replacement. Exercise backup restore into isolated state before production claims. Resource examples are 512 MiB, one CPU and 128 PIDs per API; tune from measurements.

Keep one replica; a local volume plus in-process fanout/tickets is not a shared cluster. Image rollback requires backwards-compatible data. Reconcile native resource state after interrupted operations before retrying; do not replace secrets or recreate volumes.

References: [Compose builds](https://coolify.io/docs/docs/applications/builds/docker-compose), [healthchecks](https://coolify.io/docs/applications/configuration/health-checks), [build/deployment model](https://coolify.io/docs/core/build-deployment-model).
