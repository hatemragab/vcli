# Dokploy: image + Compose, one API instance

This is an artifact/manual-operator profile. No Dokploy account, API operator, deployment, image build, migration, ingress, backup or restore has been executed by this reference delivery. Use a recorded Dokploy version and verify these instructions on an authorized test project first.

1. Build from `examples/reference-api` using `ops/Dockerfile`, inspect the image and record its registry digest. The application runs `node dist/main.js`; VCLI is absent at runtime. Do not put secrets in build arguments or build context.
2. In Dokploy create a Compose resource using this `compose.yml`. Set `REFERENCE_IMAGE` to that digest. Create stable private external volumes `reference-api-uploads` and `reference-api-evidence`; prepare and verify both mounted roots with mode 0700 and image user UID/GID 1000 ownership before starting the API. Preserve existing contents; image directory permissions do not repair mounted volumes, and the app does not change their ownership automatically. Provision an authenticated PostgreSQL database or transactional MongoDB replica set separately; this artifact does not provision it.
3. Replace the artifact's `env_file` reference with Dokploy's private runtime environment injection/advanced file mount facility. Never commit `.env.production`; deployment must stop if that required private file/injection is missing. Use the root environment contract and [operations guide](../../../docs/operations.md). SMTP and, if selected, Firebase ADC/provider credentials require separate setup.
4. Configure the native Dokploy domain UI for service `api`, container port 3100, HTTPS and WebSocket upgrades. Route `/realtime` only for Socket.IO/native ws. Deny public `/api/realtime/centrifugo/*`; if Centrifugo is selected, expose only its external `/connection/websocket`, keep internal port 9000/API private and change backend proxy endpoints to the API's private hostname.
5. After the image build, run `node scripts/migrate.ts` from `/app` as one identified release job, with the same image/private configuration, before replacing the API. It initializes identity, media, push and notes; the identity-only command is insufficient. Follow the [common release procedure and setup limits](../../../docs/operations.md#image-deployment-and-release). Stop release on failed/uncertain setup and inspect/reconcile all owner schemas before retrying; do not rerun blindly or run release setup on every API boot.
6. Deploy through Dokploy's normal lifecycle. Verify `/health/live`, `/health/ready`, authenticated note persistence, one actual realtime exchange, denial after revocation and preserved uploads after redeploy. Record digest/resource/volume IDs and sanitized assertions. Readiness is scoped to delivered dependencies; it does not prove SMTP inbox or device delivery.

Keep one replica. Rollback of the image requires schema compatibility; it never reverses data migrations. Discover resources after an interrupted operation before retrying. Preserve volume names and private values on ordinary redeploy; never use `down -v` as recovery.

Official setup contracts: [Dokploy Compose](https://docs.dokploy.com/docs/core/docker-compose), [native domains](https://docs.dokploy.com/docs/core/docker-compose/domains). Operator/API automation remains unimplemented, and target version/routing/persistence/restore acceptance is pending.
