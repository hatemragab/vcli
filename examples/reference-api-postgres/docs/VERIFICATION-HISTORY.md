## External acceptance intentionally pending

Actual Firebase email/password/phone/Google/Apple client sign-in, AWS and named compatible S3 conformance, real SMTP/domain/inbox delivery, FCM/APNs provider and physical-device delivery, Centrifugo service acceptance, container/deployed Vector/Logdy topology and viewer browser rendering, all three deployment targets, multi-instance operation and backup restore require their configured resources and separate evidence. Test doubles and the local demo do not substitute for these results.

The reference deliberately refuses presigned/multipart uploads and arbitrary custom S3 endpoints; it implements a mediated local/AWS/R2 path. Uncertain absent-object finalization requires reviewed reconciliation rather than automatic abandonment. VoIP provider construction/routing is available for an authorized internal call use case; the generic self-notification endpoint cannot invent that authorization. Durable outbox/replay, generalized upgrades, authenticated deployment operators, remote/strongly isolated diagnostics and an MCP `tests.getResult` tool are not implemented here. Those limits remain visible rather than being labeled complete.

This reference creates a fresh installation at login/bootstrap and fences push eligibility to the registering session. Stable installation reuse, cross-account device rebind, account link/unlink/deletion and application-delivered Firebase action-link workflows are not exposed. Clients must unregister destinations before logout in this limited profile; recovery/reclaim across a lost installation binding needs its own design. These are reference limitations, not removals from the wider product requirements.

Any unsupported advanced mode or security profile must remain explicit in the capability documentation and matrix. Passing local checks cannot advertise the reference as a production security-reviewed platform.
