# CapRover: native application + preprovisioned dependencies

This profile deliberately uses a CapRover app/container, not a generic Compose import. `captain-definition` selects `ops/Dockerfile`; set the Captain Definition Path to `./ops/deploy/caprover/captain-definition` while the submitted build context is `examples/reference-api`. Building or publishing is a separate authorized operation. Record the actual CapRover version; no platform/API deployment has run.

1. Create one API app through CapRover and set container HTTP port 3101, runtime variables from the root schema, a public HTTPS domain and WebSocket support. Keep the instance count at one. Use the platform's native resource-limit configuration to set an example 512 MiB and one CPU; no custom process supervisor or VCLI launcher is required.
2. Supply authenticated preprovisioned PostgreSQL or MongoDB with transactional replica-set topology, SMTP, and optional Firebase/S3/push credentials separately. Neither this file nor a Dockerfile provisions these services. Database/provider addresses must be private/restricted. A multi-service generic Compose graph is unsupported by this profile and must not be treated as imported.
3. Add native persistent directory mappings for `/app/var/storage` and `/app/var/evidence`, with stable resource identities; prepare and verify both mounted roots with mode 0700 and UID/GID 1000 ownership before starting the API. Preserve existing contents; image directory permissions do not repair mounted volumes, and the app does not change their ownership automatically. CapRover pins persistent apps to their data node; another replica/node cannot be assumed to share these files. Limit diagnostic retention in application configuration. Keep reader/viewer access separate from platform administrator credentials.
4. If using Centrifugo, provision a separate native service app with the supplied config and private port 9000. Inject API and callback secrets separately, change proxy endpoints to the API's private hostname and expose only `/connection/websocket`. Deny public backend callback paths. The image/API profile is only single-instance; external service capacity is not a cluster-certification claim.
5. After the image build, execute `node scripts/migrate.ts` from `/app` using an identified one-off release container/native task with the same image/config before replacing the API. It initializes identity, media, push and notes; the identity-only command is insufficient. Follow the [common release procedure and setup limits](../../../docs/operations.md#image-deployment-and-release). Stop on failure or uncertainty and inspect/reconcile all owner schemas before retrying. Do not run release setup independently on every API boot.
6. Deploy through CapRover's standard mechanism. Verify readiness, auth/note persistence, actual protocol exchange, idle revocation and preserved uploads after redeploy. Inspect native resource/volume IDs and record the image digest. Restore a protected backup into a separately named isolated target and verify owned account/note/upload reads before advertising recoverability.

Do not use the platform backup as proof that all application database/object/volume data is covered. Image rollback does not roll back schema/data. Discovery/reconciliation comes before retry after a timeout; no automated operator exists here.

Official contracts: [Captain definition](https://caprover.com/docs/captain-definition-file.html), [persistent apps](https://caprover.com/docs/persistent-apps.html), [persistence](https://caprover.com/docs/data-persistence). Target resource/TLS/restore verification remains pending.
