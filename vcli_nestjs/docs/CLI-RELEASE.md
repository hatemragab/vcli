# Selected release, backup and isolated restore

O1 implements the finite selected-output release and private native recovery slice for Phase08. Reference applications remain read-only historical inputs. Controlled history/command tests and isolated compilation are different from real owner migrations, native dump/restore, provider snapshots and deployed acceptance; the evidence below keeps those outcomes separate.

## Composition and source ownership

`src/recipes/render-schema.ts` retains synchronous `schemaFiles(config):RenderedFile[]`. With a selected database it emits:

- `src/generated/selected-release.ts`: `selectedReleaseManifest:ReleaseManifest` and `assertSelectedReleaseReady(database,manifest=selectedReleaseManifest):Promise<void>`, with the exact selected `PostgresDatabase` or `MongoDatabase` parameter.
- `src/generated/initialize-selected-schemas.ts`: `initializeSelectedSchemas(config:AppConfig):Promise<readonly string[]>`, now invoking the finite coordinator above the owners.
- `src/initialize-database.ts`: explicit release job; no migrations on ordinary boot.

Root imports the readiness assertion into `create-app.ts` and awaits it immediately after opening the selected database and registering its cleanup, before constructing mail, identity, media, push, realtime or other external providers. It only reads the ledger; it does not create tables/indexes, acquire a migration lock or invoke an owner. Core imports no feature or generated release composition.

`src/recipes/render-release.ts` exports `renderReleaseFiles(config):Promise<RenderedFile[]>`. Root appends these files once to its rendered output. It emits the common release types/validation/coordinator, protected files, authenticated encryption, bounded native command execution, backup types/validation/service, and only the selected `native-release-store.ts`, `native-database-url.ts`, `native-backup.ts`. It also emits the three commands below and `ops/release/README.md`. Node, the selected pg/Drizzle or Mongoose packages, and Zod supply the runtime dependencies. Isolated tests use the VCLI repository's locked development dependencies.

| Package script contribution                                 | Exact command                            | Explicit private operation input                                                |
| ----------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------- |
| `db:initialize` (retained) / optional `release:apply` alias | `node dist/initialize-database.js`       | Existing selected environment and `APP_ENV_FILE` behavior                       |
| `release:reconcile`                                         | `node dist/release/reconcile-command.js` | `VCLI_RELEASE_DECISION` JSON file path                                          |
| `backup:create`                                             | `node dist/release/backup-command.js`    | `VCLI_BACKUP_PROFILE` JSON file path plus selected environment                  |
| `backup:restore`                                            | `node dist/release/restore-command.js`   | `VCLI_RESTORE_PROFILE` JSON file path; source credentials/config are not loaded |

These are coordinator-owned package/composition integrations, not new VCLI top-level commands. No shared AppConfig fields, provider catalog choice or runtime DB selector is added. Native dump/restore tools are **operator-host prerequisites**, not promised API-image binaries. Release initialization uses the existing Node native SDKs and is suitable for the separately rendered release job. Operation profiles/keys belong outside the image context or in ignored `.vcli/local`; archives/work roots remain separately private. O0 owns actual image/context/service integration.

## Identified releases and history

The manifest has `{schema:1,id,components:[{component,version,digest}]}`. Its selected identity is `selected-v1-` plus a technical digest prefix. Component digests bind an explicit static list of bundled schema/migration contributions; no directory is evaluated or scanned for developer migrations and no private environment or key is read/hashed. Currently registered callbacks are:

| Component/version          | Selected condition | Owner API                                                                                                                                |
| -------------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| identity/4                 | auth               | `initializeIdentityDatabase(config)` opens and closes its native resources and preserves existing 001/002 or identity/lifecycle markers. |
| mail/1                     | reliable mail      | `initializeMail(database)` on an explicitly opened selected DB                                                                           |
| media/1                    | media              | `initializeMediaSchema(config)`; owner opens/closes its selected store                                                                   |
| push/1                     | FCM or APNs        | `initializePushSchema(config)`; owner opens/closes its selected store                                                                    |
| realtime.TRANSPORT.SCALE/1 | realtime           | `initializeRealtime(database)`; selected protocol/scale identity, no import when absent                                                  |

Realtime component IDs include the selected transport and scale, such as `realtime.native-ws.single-instance` or `realtime.socket-io.cluster`. Cluster Socket.IO additionally hashes its selected `initialize-socket-io-cluster.ts` owner contribution. A previous single-instance success cannot suppress newly required cluster DDL; the new identified owner executes and later preserving repeats skip it. Digests use explicit selected paths with the same ENOENT-only variant/common fallback as bundled runtime assets, including Mongo push storage; location-only dedup preserves the logical contribution digest.

Identity version 4 fingerprints the schema selected for username, email, or Firebase authentication. A fresh database creates the selected durable auth stores, including action-token or provider-cleanup stores where applicable. Redis holds the expiring rate-limit counters. Applying the release to a database with completed native identity markers preserves existing tables, collections and history, including any legacy rate-limit store.

Schema callbacks perform no Firebase, SMTP, S3, FCM, APNs or Redis operation. Register custom schema owners in the developer-owned `src/release/custom-migrations.ts`. Each entry supplies a stable `app.*` component, positive version, SHA-256 digest of the reviewed schema steps, and an `apply(database)` callback typed to the selected native database. Keep entries in dependency order. Each version must preserve data and support a fresh or previously supported database. The generated `ops/release/README.md` includes a selected-native example. The release command, boot, reconciliation and backup use the same combined manifest. An empty list retains the historical built-in release ID and digests. Changing already acknowledged component bytes without advancing its version fails. Do not edit an acknowledged migration in place or assume generated managed files can overwrite customized business code. Release/backup implementation files are developer scaffolds; composition/commands/manifest are managed technical output subject to engine preconditions.

`ReleaseCoordinator` takes a small `ReleaseStore` and exposes `apply(manifest,owners)` and `reconcile(manifest,quiescedDecision)`. Owner order must exactly match the manifest. Callbacks execute once per attempted owner outside retryable ledger/native transactions; this is not a global exactly-once promise. A callback may have committed its own schema work before throwing. Completion acknowledgement loss can also be uncertain. The coordinator therefore persists an `incomplete` attempt before invoking the owner, acknowledges `completed` afterward, and records `unknown` on a caught uncertain result when the fence still permits that write. It never turns unresolved work into a retry or success automatically. Already successful owners remain recorded and are skipped on a reconciled retry.

Both variants use a singleton `vcli_release_history` ledger with preserved manifests, component/version/digest attempts, fences, resolutions and nonsecret operator evidence references. PostgreSQL stores JSONB under a dedicated connection/session advisory lock **61921234**, distinct from identity's transaction lock **61921233**; the owner initializer can use its separate connection without self-deadlock. Mongo stores one bounded document with majority writes, permanent holder token and monotonically increasing fence/revision; every mutation compares token/fence/revision atomically. There is **no TTL or lease expiry takeover**. History is bounded at256 manifests,2048 attempts,256 operator decisions; exhaustion refuses additional history rather than deleting it. A deliberate developer ledger migration/archive procedure is needed before increasing capacity.

After all owners succeed, the manifest is acknowledged and becomes `currentRelease`. Older manifests and successes remain historical; boot and reapply reject an older completed manifest after a newer release. A newer component version also rejects an older desired version. Digest/identity mismatch, missing history, active holders and unresolved attempts deny readiness. This is an exact selected-release gate, not an expand/contract or code rollback compatibility claim. Application image rollback does not reverse schema/data changes.

Concurrent PostgreSQL sessions refuse the held advisory lock. Mongo refuses an existing durable token; time passing does not prove previous work stopped. A process crash may leave a holder and incomplete attempt. After actually stopping every old release runner and relevant writer, inspect owner state privately and use:

```json
{
  "quiesced": true,
  "expectedHolder": null,
  "expectedFence": 3,
  "evidence": "ticket:inspected-owner-and-stopped-runners",
  "attemptId": "the-exact-attempt-id-from-private-history",
  "decision": "retry"
}
```

Use the actual UUID holder when retained. `decision:'completed'` asserts independently inspected owner completion; `retry` explicitly accepts possibly repeating already committed native work. Omitting both attemptId/decision only fences an orphaned holder and records the operator decision; unresolved attempts remain blocking. Stale holder/fence decisions fail. PostgreSQL also refuses recovery while a live session still holds its lock. Mongo fencing prevents stale ledger writes; it cannot terminate an old native callback, so the quiesced operator attestation is mandatory. Do not infer safety from a clock, expired lease, process-status uncertainty or a failed release command.

## Quiesced private native snapshots

The generated [runbook](../templates/runtime/common/ops/release/README.md) is part of every selected DB output and specifies every profile field. `BackupService.create(databaseUrl,manifest,profile,coverage)` validates exact configured roots/resources/secret-source references and returns nonsecret identities with `restoreVerified:false`. `BackupService.restore(profile)` returns `restored-unverified`, even after the native command and restored release check succeed. Neither is provider/application restore acceptance.

Before creating a backup, the operator stops API and all background writers, mail drains, upload/finalization/deletion, cleanup, realtime shared-state writers, schema runners and relevant external object writers for the full snapshot. Native DB snapshots alone cannot synchronize files or remote objects. The simple supported profile relies on explicit `quiesced:true` and a nonsecret `quiescenceRef`, then captures the native database and exactly selected private media roots. PostgreSQL custom-format `pg_dump` makes a database snapshot; Mongo `mongodump --archive --gzip` is used only under this quiesced profile, without claiming online cross-resource consistency or oplog replay. No provider network is called by source schema release.

The operation profile names a new archive directory, existing private work directory, external raw32-byte archive key file and key ID, byte/file limits, exact local root IDs/paths and operator policy references. Paths reject traversal, symlinks, special files, insecure permissions, overlapping archive/work/key/media roots and existing archive destinations. Local storage is exactly `[{id:'media',path:LOCAL_STORAGE_ROOT}]` when selected, including S3 staging. Detailed inventory and each database/media payload use independent random-IV AES-256-GCM encryption bound to backup/root/entry identity. Plaintext dumps are transient in a private work directory; all files are0600 and directories0700. A final public `backup.json` contains only backup/key/release identities and technical release digest. It is written after authenticated payloads; incomplete archives are preserved for private operator review, with no successful identity marker. Work files are removed in `finally`; abrupt host/process death can leave identified private transient files for operator cleanup.

PostgreSQL password values live only in temporary0600 exclusive/nofollow pgpass files via `PGPASSFILE`, with explicit nonsecret PG connection environment. Mongo places the full sensitive URI in a similarly protected temporary YAML `--config` file. Child execution uses argument vectors, bounded timeout, no shell, a minimal explicit environment and discarded raw stdout/stderr. Commands do not inherit arbitrary user PG/Mongo credentials, start services or install tools. The bounded URL profile accepts explicit safe database/user names and documented SSL/query options; unsupported multi-seed/custom auth/tool connection options fail instead of falling back. Native credentials are removed on normal/failure completion. Archive keys, signing rings, mail delivery keys, provider credentials and private env are never included in snapshots or plans.

Policy fields identify restricted backup access, retention-until and independently maintained secret-source references. Required generated secret-source names are `database.credentials`, selected `identity.signing-key-ring` or `identity.firebase-credential-source`, and reliable-mail `mail.delivery-key-ring`. These are identifiers, not copied secrets. The backup profile must list every currently configured mail encryption key ID and all additional historical IDs required by retained encrypted payloads; restore requires availability of every recorded ID. Key-material availability/decryption and post-restore grants remain operator evidence. Encryption alone does not implement ACL provisioning, retention deletion or a scheduler.

AWS/R2 require an exact `aws:BUCKET`/`r2:BUCKET` `ExternalSnapshot` with provider, immutable snapshot reference, access-policy reference, restore-contract reference and retention at least the archive policy. This contract must cover every database-referenced immutable object version plus the matching quiescence boundary. **Remote bytes are not copied or verified by this implementation.** A DB-only archive with absent configured remote coverage fails. The provider-native contract must separately support isolated object copying/rebinding or strictly immutable read references without exposing production writes. Restore reports `externalContent:'reference-contract-only'`, checks referenced access/retention availability, and never treats local archive success as S3 content restore proof.

## Isolated restore safety and verification

Restore takes its own private profile and target credentials; it does not load source environment values. It requires `isolated:true`, `targetEnvironment:'isolated'`, quiescence reference, a distinct DB resource ID, **target DB name matching `vcli_restore_[a-z0-9_]{1,48}`**, a different source database name and no protected production name. This conservative namespace plus native empty-target checks prevents an arbitrary production-named URL from being relabeled as isolated. The operator must still supply an actually isolated account/network/resource: a caller-controlled label cannot establish provider isolation. Storage destinations must be absent, private, disjoint from every source root and each other; traversal, symlink ancestors and overwrite attempts fail. Source DB/volumes/credentials and encrypted archive contents are never reset.

All authenticated payloads are checked and staged before native DB execution. PostgreSQL reserves a persistent target guard while holding separate advisory lock61921235, refuses every preexisting user relation, and uses `pg_restore --single-transaction --exit-on-error --no-owner --no-privileges` into the explicit target, without `--create`/`--clean`; source DB name/ACL/ownership are not replayed onto the source. Establish target least-privilege grants separately. Mongo atomically reserves a guard collection after checking emptiness, then restores using `--nsInclude=SOURCE.* --nsFrom=SOURCE.* --nsTo=TARGET.* --stopOnError --numParallelCollections=1` with target URI database removed and its authentication database preserved. Archive `--db` semantics and `--drop` are deliberately absent. A failed Mongo restore can leave partial target content; a persistent guard makes reuse fail rather than overwrite. Failed targets/media remain private for inspection and require a fresh target/destination for another attempt.

After native restore the service validates restored release history. Independent root acceptance must then assert known rows, exact private object bytes, historical mail-key decryption, selected application behavior, least-privilege access and any external immutable-object contract. A zero native exit alone does not provide this evidence. Deployed restores, backup hosting, provider snapshot implementations and production changes remain separately authorized external work.

## Evidence and root fixtures

Worker checks run only against installed packages/caches. All emitted compiler/test artifacts are confined to ignored `var/cli-release`; no root/reference dist output, installations, Docker, shared service, preview/browser, provider accounts or external test network is used. The controlled suite tests history preservation after failure, exact reconciliation, before/after completion acknowledgement loss, concurrent denial, old-fence denial, stale/changed manifests, selected realtime registration, selected source/command compilation, authenticated private file round trip, tamper/wrong-key rejection, missing historical keys/object coverage, path/production/overwrite refusals and private temporary credential cleanup with injected command runners.
