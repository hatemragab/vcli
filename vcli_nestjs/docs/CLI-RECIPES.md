# Curated CLI recipes

The private local CLI exports `recipeCatalog` and `renderScaffold` from `src/recipes/index.ts`. Rendering is asynchronous, deterministic and read-only. It returns desired files, scoped check commands, warnings and explicit manual or external work. The engine resolves requirements and applies ownership and preconditions. Rendering validates the selection again. Changes to exclusive installed providers require a reviewed migration.

Bundled trusted assets under `templates/runtime/` are package contents. Generation reads them relative to the installed module, never from repository examples or absolute contributor paths. Both native variants are included as CLI tooling; only the selected variant is emitted to application source and dependency declarations. Generated apps pin the private coordinated CLI through `@vcli/cli: file:tools/vcli`; the coordinator bundles that local CLI distribution. This is not a registry ownership or publication claim.

Firebase defaults to all four `email-password`, `phone`, `google`, `apple` methods and `actionDelivery:'provider'`. A nonempty distinct subset is allowed. Provider mode uses the client SDK and needs neither application mail nor local JWT. Application verification/reset links require selected reliable mail and the server-controlled continue/Hosting/mobile policy. Local auth uses a private bounded JWT key ring and the narrow optional-peer auth runtime. See [identity](CLI-IDENTITY.md) and [mail](CLI-MAIL.md).

New projects with `--auth local` use basic email/password auth. `--local-identifier username` selects normalized usernames. Basic persists `auth.local` with `{ "profile": "basic" }` and includes `"identifier": "username"` for username auth. Existing config and lock files with an omitted profile select the existing full implementation. Explicit `--local-auth-profile full` normalizes to that same option shape. Regeneration preserves the installed profile and identifier mode. [Basic local authentication](CLI-IDENTITY.md#basic-local-authentication)

Basic auth adds no mail provider by default. Select `--mail smtp`, `--mail http`, or `--mail capture` explicitly for application mail. Full local auth adds rotating refresh tokens, installation possession, and account/session lifecycle. Private media, push, realtime, and the Notes example require full local auth or Firebase. Full local email auth uses a mail provider for verification and recovery. Full username auth uses `--local-auth-profile full --local-identifier username` and retains authenticated password change. [Mail contract](CLI-MAIL.md) · [Full local username authentication](CLI-USERNAME-AUTH.md)

Diagnostics defaults to application evidence with MCP/Vector/Logdy/testCapture disabled and `reader:'local-same-user'`. Optional sources are workers, database, infrastructure and tests; database requires the selected native DB, and test capture requires tests. Restricted remote reads use an explicit private scoped profile. Isolated/shared-production diagnostics, arbitrary custom S3, native-ws cluster, durable realtime replay and queued push dispatch are unsupported; selection rejects unsupported options before mutation.

A minimal selection has only `foundation.nest`. It emits ordinary Nest build/start/watch scripts, explicit health initialization/shutdown state, selected environment validation, redacted structured logging and safe HTTP errors. It contains no database, authentication or provider SDK. Every selected family adds its own imports, dependencies, environment keys, runtime composition, assets and guidance. Application dependencies are pinned from reviewed reference versions using only actual emitted imports; unmapped imports fail rendering. No application package lock is invented: package installation and closure verification are coordinator acceptance steps.

Configuration validation, development defaults and deployment environment keys use one selected field model. Fresh init and saved init plan application write a gitignored, mode `0600` `.env.development`. Apply generates fresh development keys for the selected local JWT, reliable mail, and Centrifugo capabilities. Local storage init also creates a private, Git-ignored `storage/` directory. The file belongs to the project owner and later generation preserves it. Required external provider settings come from the operator. `APP_ENV_FILE` can select a private file, and process environment values take precedence over its contents. Set production configuration privately and use separate signing keys. Runtime provider-selector variables are rejected because source selection is fixed.

All selected authentication profiles use Redis for expiring rate-limit counters. The generated development file sets `REDIS_URL=redis://127.0.0.1:6379`. Production must supply `REDIS_URL` privately. The native database owns accounts and, for full local or Firebase auth, their installation, session and revocation state. `init --redis-docker` emits an optional loopback Redis Compose file for local development. [Identity contract](CLI-IDENTITY.md) · [Local service commands](CLI-OPERATIONS.md)

Owner account/identity/session persistence, refresh atomicity, private-media state transitions, push fencing and protocol cleanup are selectively bundled from the reviewed native runtime. `VcliAppModule` uses static Nest imports for the selected modules. Each provider module exports its injectable service. A custom consumer imports the provider module directly. Database initialization imports only selected owner schemas and ships the PostgreSQL SQL asset when needed. Media/push schema initialization is explicit and application startup does not create their schemas.

The `api` preset requires a database and defaults to basic local auth, local storage, and diagnostics. With full local auth or Firebase, it also includes private media, Socket.IO by default, and `example.notes`. The explicit Notes recipe provides an owned REST example and optional realtime hints. Realtime consumers recover authoritative state through owner REST reads. Owner persistence classes and business helpers are scaffold-owned; additions preserve their bytes. Tool-owned composition, provider selection modules, configuration, selected operation artifacts and bounded guidance/package fields are managed. README and AGENTS managed text is enclosed by `<!-- vcli:managed:start -->` and `<!-- vcli:managed:end -->`; the engine preserves prose outside those markers and unknown package keys. `AppCustomModule` is developer-owned. Add `ProjectItemModule` to its `imports` array to enable that scaffold. `ProjectItemModule` imports `DatabaseModule` and any capability modules selected with `--use`. Copied runtime security updates need a reviewed manual patch or a narrowly approved codemod when source has been customized.

`renderScaffold(config, {kind, name})` supports `feature`, `service`, `controller`, `dto`, `repository`, `command`, `query` and `realtime`. Names are bounded kebab-case identifiers and cannot collide with built-in owner modules. Files are scaffold-owned and include explicit integration instructions. A database feature or repository uses its selected native `BaseRepository` and schema, with schema initialization/migration left explicit. Controllers contain no routes, commands/queries throw a named unfinished-operation error, and DTOs start with an empty strict schema. Realtime scaffolds delegate typed publication to the selected service and require explicit consumer-module imports and trusted ownership policy. No arbitrary consumer source is rewritten.

Implemented runtime contracts are documented separately: [identity](CLI-IDENTITY.md), [mail](CLI-MAIL.md), [push](CLI-PUSH.md), [storage/media](CLI-STORAGE.md), [notes](CLI-NOTES.md), [realtime](CLI-REALTIME.md), [diagnostics](CLI-DIAGNOSTICS.md), [operations](CLI-OPERATIONS.md), [release/restore](CLI-RELEASE.md), [native deployment operators](CLI-DEPLOYMENT-OPERATORS.md) and [maintenance](CLI-MAINTENANCE.md). This catalog describes source support; exact local, synthetic and real-service evidence is recorded in those contracts and [CLI verification](CLI-VERIFICATION.md).

External Firebase client methods/action links, SMTP/domain/inbox, Resend, FCM/APNs/device behavior, AWS/R2 and all live target/TLS/persistence profiles remain separate pending resources. Source or controlled protocol tests do not establish their acceptance. Deployment cluster support rejects private local storage/evidence roots; external shared DB and the selected realtime engine/adapter must meet the explicit profile. Durable mail is implemented with encrypted native intents; push remains an immediate fenced operation.

Every generated app has architecture and fixed-database isolation checks wired into check and prebuild. The checks include type-only import cycles, feature direction, one class per file, forbidden loading shortcuts and declared/locked opposite-database closure; the foundation gate rejects either database implementation.

Scoped tests assert selected file, import and dependency sets, four authentication/database outputs, deterministic rendering, schema assets and scaffold ownership. After `npm ci` and `npm run build` at the VCLI root, `node --test test/recipes-compilation.test.ts` compiles, lints and checks the architecture of eight disposable generated profiles using the root lockfile’s dev dependencies. The profiles cover minimal and capture-only apps, both auth/database combinations, local/Socket.IO and R2/Centrifugo. This provides static evidence. The install, build and boot gates use each generated app’s own manifest and dependency tree.
