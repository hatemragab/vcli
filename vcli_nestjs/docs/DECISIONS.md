Revision 0.2, 16 November 2026. These are the recommended implementation baseline synthesized from the discussion and independent reviews. Preparing this document does not record owner approval of every recommendation and does not authorize implementation. Phase 00 records accepted choices and deviations before dependent work.

## Deferred options

Public plugin execution, plugin marketplace, arbitrary existing-project adoption, automatic database/provider migration, generalized source merging, runtime package ejection, extra ORMs, full frontend application generation, custom supervision, mutating MCP tools, and transparent refresh-response recovery are deferred unless explicitly added to scope. Their absence does not remove the requested provider families.

## Owner-authorized reference application, 16 November 2026

The owner requested a working hand-built example of expected generated output before implementing VCLI, using public npm packages, SOLID and the existing coding rules. The reference lives under `examples/reference-api`; this scope does not complete Phase 00 or authorize CLI implementation, registry publication, provider provisioning or production deployment.

The owner selected MongoDB/PostgreSQL as alternatives for the same capabilities, then clarified that the choice is made once at project init. The former runtime-profile catalog is superseded by separate MongoDB-only and PostgreSQL-only reference projects, with local real-database acceptance and external provider verification kept separate. The reference includes both local and S3 storage adapters, selected explicitly at runtime, a Makefile delegating to ordinary package scripts, explicit test configuration, and production-like staging guidance. Existing objects retain their provider references; changing a driver does not migrate data.

The reference reuses the available Node 26.13.1/npm 11.20.0 toolchain, exact compatible public dependency pins and cached artifacts. This is a contributor/reference choice, not a silent replacement of the recommended future pnpm CLI baseline. Its own verification record separates static, fake, real local database/protocol/browser and external evidence. A hand-built reference does not supply generator ownership, dry-run, safe-add, recovery, packaging or upgrade proof.

The tested reference uses explicit Zod input parsing at transport boundaries and Zod-derived/explicit OpenAPI descriptions; it does not assume a native/official Zod pipe exists for the chosen Nest version. Its fresh-installation-per-login policy and unavailable advanced modes are prototype limits documented in the reference, not changes removing requirements from the phase plan.

The reference's email-confirmation request explicitly includes the password chosen by the holder of the one-use email proof. Confirmation atomically establishes that password, advances credential version and verifies the account; it never activates an earlier unverified registrant's password implicitly. This policy resolves the duplicate-signup pre-hijacking case found during review. It changes only the unreleased reference contract and must be retained in future generated-app acceptance.

## Owner-approved simplification, 16 November 2026

After inspecting the working reference, the owner requested flat feature modules following the supplied API-token example: entity/schema, injectable service extending BaseRepository, and Nest module exporting the service. Controllers/DTOs and focused helper services exist only when needed. This supersedes the earlier mandatory layered-directory recommendation. Shared repositories, transaction coordination, page pagination, auth guards/current principal, validated configuration and safe HTTP errors live under core. Mail, storage, push, realtime and diagnostics expose directly injectable services.

The owner expressly prohibits circular dependencies and forwardRef. Both runtime/type file imports and feature dependency graphs are checked; core imports no features, and locator/global/lazy-import workarounds are prohibited. Schema setup and multi-feature orchestration sit above participants. The independent reference projects each contain one database. A future init command chooses and emits only that native implementation, schema/config and dependency closure. This refactor does not implement VCLI or erase external acceptance limits.

## Native database repository expansion, 16 November 2026

The owner explicitly rejected the runtime BaseRepository adapter selector and authorized implementing the richer helper catalog. Each generated-style app contains one database chosen during init. MongoDB uses native Mongoose model/query/session capabilities; PostgreSQL uses Drizzle/pg, typed SQL predicates/joins and explicit upsert conflict targets. No production memory database, Database union, RepositoryAdapter or combined per-entity Mongo/SQL definitions remain in the intended output. Unit test doubles are test-owned.

The owner approved common create/read/count/distinct/pagination/update/upsert/delete helpers, returned-record versus write-result semantics, projected result types, stable bounded pagination/iteration, explicit whole-collection bulk opt-in and shared transaction participation. Mongo aggregation/population/bulk and PostgreSQL native joins/grouping/batches remain provider-specific. Existing authority, credential, session, storage and push atomic invariants must survive expansion. Native implementations passed separate real-database, HTTP/protocol and browser/restart acceptance; see each reference verification record. The owner subsequently authorized implementing the full CLI through the phase gates.

## Shared reference logging, 16 November 2026

The owner authorized improving the example's logger before completing the documented Vector/Logdy integration. The two independent reference projects use a shared injectable `AppLoggerService` backed by their already pinned Pino dependency. Bootstrap, Nest, HTTP and realtime emit the same validated, allowlisted application event facts. The composition root opens and closes the existing bounded retained writer independently of realtime, beginning before database/provider setup; invalid configuration before that safe setup is stdout-only. Explicit Nest imports/exports replace neither dependency boundaries nor normal composition with a global module.

The retained application topology is emitter validation -> bounded rotated JSONL -> Vector normalization/revalidation -> privately bound Logdy live feed. The offline reader/MCP reads those same application files directly and does not depend on Vector or Logdy availability. This supersedes the earlier Phase 07 wording that placed application JSONL retention after Vector. Pino stdout is an operator output, not an additional collected source in the supplied Vector profile. Safe correlation propagates through asynchronous application work; HTTP terminal operation events do not prove external recipient delivery or replace assertions.

Native Vector 0.62.0 transform tests and the Logdy 0.17.1 loopback backend feed have recorded evidence, including retention after viewer termination. Docker/host-gateway topology, viewer browser rendering, reconnect/overload acceptance, worker/database/infrastructure collection, source-specific sanitization and retention, remote/isolated profiles, deployed access boundaries and test-result capture remain separate pending capabilities. Inline Vector transform tests are necessary configuration evidence, not proof of those runtime guarantees. The examples remain hand-built references and do not complete VCLI generator phases.

## Full CLI implementation authorization, 16 November 2026

After reviewing the flat modules and native repositories, the owner authorized orchestration and implementation of the full CLI catalog through all documented phases. Use public npm packages when useful, the approved simple entity/service/module structure, one class per file, one database chosen at init and enforced acyclic dependencies without forwardRef. Complete phase gates autonomously within this scope. This authorizes source implementation and local acceptance; registry publication, provider provisioning and production deployment still require their own authorization. External accounts/devices and unsupported modes remain explicit rather than being represented as locally verified.
