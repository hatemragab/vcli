## Options, environment and persistence

`media.private.options.modes` is an explicit nonempty subset of the selected profile, default `["mediated"]`. Root owns catalog/planning validation and shared config. The renderer independently rejects unsupported modes before emitting files. `MediaHttpOptions` gains optional `modes`; maximum/ttlSeconds/profile/stagingRoot remain. `config.storage.modes` is the corresponding readonly UploadMode array. Existing `UPLOAD_MAX_BYTES` (max100 MiB), `UPLOAD_TTL_SECONDS` (max900 seconds), private local root and selected S3 fields are reused. No new secret env field is needed. Credentials use private SDK credential providers; they never appear in grants or templates.

The selected DB media directory owns entity/repository/service/controller/transitions/decoder and its native store; Mongo's store source remains common and uses its native connection. New optional owner-entry fields are `mode`, `attemptId`, `generation`, `claim`, `multipart`, `objectEvidence`, `deleteAfter`, `stagingPending` and `stagingCleanupAt`. Mongo's owner-document revision CAS and PostgreSQL's owner-row lock serialize quota/reservation/claim/part changes. No provider work runs inside those callbacks. An opaque claim token plus exact attempt/generation fences every publication and cleanup. Declared part length/hash cannot be replaced. The existing `app_media_owners` collection/table is sufficient: no new collection/table or DDL migration is introduced, and the decoder accepts historical mediated entries. Root retains that owner in app-schema release. No schema startup/provisioning occurs in application boot or opt-in tests.

Reservations include ready bytes and all outstanding/failed/deleting attempts; max4 outstanding attempts,128 entries and256 MiB per owner. At most4 process transfers share the storage gate; a part buffers at most8 MiB before provider I/O. Streams have30-second cancellation, provider RPCs20-second abort deadlines, claims180-second operation grace and cleanup batches at most8 entries. A stalled iterator is interrupted by cancellation. Direct AWS POST is replayable: its policy bounds each request, while provider ingress concurrency is outside the backend's process gate. Select mediated mode when backend transfer concurrency control is required.

## Modes and protocols

| Profile             | mediated single       | direct single                                            | backend multipart                  | immutable ready                                       |
| ------------------- | --------------------- | -------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------- |
| local               | bounded server stream | rejected                                                 | rejected                           | exclusive private hard link                           |
| AWS S3              | bounded server stream | exact content-length-range and signed SHA256 POST policy | bounded authenticated server parts | server-only conditional PUT plus full-object readback |
| named Cloudflare R2 | bounded server stream | rejected                                                 | bounded authenticated server parts | server-only conditional PUT plus full-object readback |

AWS direct additionally requires a **never-versioned private general-purpose bucket**. Each grant checks GetBucketVersioning and rejects Enabled/Suspended, so replay cannot accumulate unbounded staging versions. The role needs `s3:GetBucketVersioning`. Operators must keep that prerequisite while grants remain live. Mediated/multipart can use versioned buckets and persist the returned immutable version. R2 uses the named HTTPS account endpoint/auto region, atomic conditions and Content-MD5; it omits AWS SHA256/SSE headers and still verifies full-object SHA256 in application code. Arbitrary custom endpoints and unsupported modes fail closed.

Preserved routes: POST `/api/media/uploads`, PUT `/api/media/uploads/:id/content`, POST `/api/media/uploads/:id/finalize`, GET `/api/media`, GET `/api/media/:id/content`, DELETE `/api/media/:id`, POST `/api/media/cleanup`. Begin preserves mediated default, strict filename/length/SHA256 input and returns the authenticated binary PUT path. Other optional modes must be selected explicitly.

Additional routes:

| Request                                          | Operation                                                                                                      |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| POST `/api/media/uploads/:id/grant`              | Reissue AWS bounded POST fields within the original expiry; never extend the attempt                           |
| POST `/api/media/uploads/:id/parts`              | Declare `{partNumber,bytes,sha256}`; return authenticated bounded PUT path and expiry                          |
| PUT `/api/media/uploads/:id/parts/:part/content` | Exact application/octet-stream bytes; return persisted part receipt with opaque ETag                           |
| POST `/api/media/uploads/:id/finalize`           | Multipart body `{parts:[{partNumber,sha256,etag}]}` in ascending exact order; single modes use `{}`            |
| POST `/api/media/uploads/:id/reconcile`          | Recover unknown initiation/completion or retry exact deletion; unresolved outcomes remain errors/pending state |
| POST `/api/media/uploads/:id/abort`              | Fence and delete the exact unfinished attempt; active claims conflict                                          |

Direct grants authorize only private mutable **staging/**. Append all returned POST fields unchanged, then the file last; send no app auth or invented checksum headers to the bucket. Finalize obtains exact length/hash into immutable private local staging, then uses conditional PutObject on a separate ready key unreachable by the grant. It verifies the complete ready object before committing ready, retaining ETag/version evidence. Replayed staging writes cannot change a ready object. No CopyObject destination-condition assumption is made.

Multipart initiation is backend-owned and stores intent before RPC. Lost initiation acknowledgement is reconciled with a bounded exact-key multipart listing, never blind re-initiation. Parts have fixed8 MiB size except the final part, an exact declared SHA256 and length, and one serialized claim. The backend checks the bounded stream before UploadPart. A lost part acknowledgement permits only the same declared bytes to be resent; a completed part replay verifies bytes without another provider write. Completion freezes the exact stored manifest, uses a condition on completion itself, reads the staged full object and promotes separately. Multipart ETag is never treated as full SHA256. Conflicting/replaced/duplicate manifests cannot mutate ready bytes.

Provider success followed by DB failure retains finalizing intent and private spool; reconciliation reads the same immutable ready key and commits the original evidence. No acknowledgement alone creates ready. Unknown outcomes remain distinguishable from integrity/conflict/expiry. Deletion keeps a tombstone and reservation through operation grace (and through outstanding direct-grant expiry); cleanup resweeps the exact key/version before forgetting. An older generation's cleanup cannot touch a replacement. Ready entries expose `cleanupPending`; failed private-spool/remote-staging cleanup remains persisted and is retried in bounded cleanup batches after the grant horizon, without deleting ready objects. Aborting an unknown finalization removes public eligibility while preserving this cleanup fence. Failed deletion remains deleting and retryable. Expired finalizers can be reconciled or explicitly aborted; an outage never becomes fabricated success.

The browser example is `clients/media-client.ts`; it uses actual returned POST fields, mediated part grants and receipts, exact manifests, current private session headers, and explicit reconcile/abort paths. The caller supplies a precomputed full-object SHA256; per-part browser hashing is bounded to8 MiB. A pending result preserves its upload ID; callers resume that attempt rather than creating a new provider key. `ops/storage/private-storage-setup.md` is filtered to the selected provider, with direct-only `aws-cors.example.json`. These are setup/client artifacts, not browser/provider acceptance.

## Filesystem, serving and setup

Private local roots/areas are owned0700. Linux proc-fd directory anchors, exclusive/no-follow opens, immutable0400 files, exclusive hard-link promotion and directory sync avoid traversal, symlink and ancestor-rename redirection. `/proc/self/fd` must be available; unsupported OS/filesystem hosts fail explicitly. The application OS owner is trusted; private storage is not a same-user sandbox. Use durable volumes and declare single-instance or verified shared-volume topology; independent per-container disks do not provide shared media. Back up local objects with their owner DB and stored profiles.

All downloads use current authenticated authority, the stored immutable reference and attachment/octet-stream/nosniff/sandbox/private-no-store responses. Filename and MIME remain untrusted metadata. No public static directory, public bucket, inline active content, scanning, public CDN or instant revocation claim is introduced. Logout blocks new mediated operations, while existing direct POST fields can write only staging until their original expiry.

Provider setup requires private bucket/IAM, exact authorized browser CORS origin for AWS direct, backend multipart permissions, bounded abandoned-upload and staging/noncurrent-version lifecycle policies. Never expire ready media with the staging rule. Signed URLs/form fields and credentials must be excluded from diagnostics/logs. Source only provides these runbooks; no resource provisioning occurs.
