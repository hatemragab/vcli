# Selected identity lifecycle contract

The identity subsystem retains disabled/deleted account tombstones, identity subject keys, immutable capability hashes and revoked session/family records. Self deletion disables account access and clears the account email and password hashes atomically; it does not erase unrelated application data, audit records, backups or Firebase data before provider cleanup completes. Application owners must supply their own business-data retention/erasure procedure. Responses explicitly report `applicationCleanup: 'required'`, and provider cleanup is separately pending until acknowledged. No automatic retention purge or subject reuse is supported: keeping subject tombstones also fences delayed or unknown destructive provider calls from a replacement binding. Disable is irreversible through public self routes; operator recovery requires a separately reviewed process. This conservative policy is frozen before exposing self-action routes.

Every self disable/delete/provider-wide revoke requires explicit action confirmation and a fresh password (local), or a recently authenticated verified Firebase proof for the current session subject. Ordinary session current/selected/others/all revocation changes application authority and enrollment cutoff only; it never invokes Firebase account-wide revocation. External provider work runs outside transaction callbacks, from bounded durable intent. Unknown acceptance remains visible and locally revoked authority survives restart/outage.

Installation possession is independent of session possession. Clients generate canonical 32-byte base64url `installationCapability`, keep it privately, and reuse it for logins/bootstrap; `allowRebind: true` is explicit confirmation to switch a proved installation after fresh authentication. An ID alone proves nothing. Every binding change increments durable generation and revokes old-generation sessions in the same transaction. Lost installation capability requires creating a new installation and explicitly revoking old sessions, not recovering by ID or email. Delayed push/realtime/application work must recheck both session authority and the exact installation generation immediately before disclosure.

Firebase clients generate `sessionCapability` once per intended application session and retain it across bootstrap retries and ID-token refresh. POST `/api/identity/firebase/bootstrap` accepts `{idToken, sessionCapability, installationCapability, allowRebind?, platform?}`. `X-Session-Token` carries the raw session capability privately on authenticated requests; the safe bootstrap response contains only sessionId, installationId, installationGeneration and expiresAt. A live capability recovers the same session despite old auth_time; a new capability requires recent auth_time and the durable account cutoff. Revoked, expired or rebound capabilities never reactivate. No `iat` freshness or email merge is used and no second JWT pair is issued.

## Generator and composition contract

`src/recipes/render-identity.ts` emits the selected identity module, owner source, common `src/core/auth/{auth-runtime-error,password-input,session-record}.ts` helpers, native cleanup types, selected client and identity schema assets. Root renderers retain configuration, package distribution, application composition and the combined schema entrypoint; identityFiles does not emit `src/initialize-database.ts`. Native schemas remain separate, never runtime-switched. initializeIdentityDatabase explicitly applies PostgreSQL001 then002, or Mongo base collections/indexes then all three owner lifecycle contributions. Ordinary boot validates both markers and never applies migrations.

`new JoseAccessTokens(policy: JwtPolicy)` takes the exact auth-runtime policy. Private `JWT_KEYS_JSON` is a strict JSON array of 1–4 `{ "id": "rotation-id", "key": "canonical-base64url-of-32-random-bytes" }` entries; no other keys. Decode canonical base64url into Uint8Array, never UTF8 key text. `JWT_ACTIVE_KID` selects an explicit entry. Existing JWT_ISSUER/JWT_AUDIENCE map directly; `JWT_MAX_LIFETIME_SECONDS` maps to maxLifetimeSeconds (1–86400, default900) and `JWT_MAX_FUTURE_ISSUED_SECONDS` to maxFutureIssuedSeconds (0–60, default0). Require access TTL <= maximum lifetime. Runtime snapshots keys; replacing config requires replacing the wrapper. Existing `JWT_SECRET` is superseded. Examples contain blank keys only. Firebase opaque mode needs neither this config nor JOSE/Argon peers.

`await ArgonPasswords.create(policy?: Partial<PasswordPolicy>)` shares one bounded runtime across hashing, verification and dummy verification. The application enforces exactly 12–128 UTF16 units, <=256 UTF8 bytes, well-formed Unicode, without normalization/truncation. maxPasswordBytes is fixed256 by the wrapper. Passwords now exposes verifyDummy(password):Promise<void>, replacing public dummyHash. The wrapper maps fixed runtime codes through safe ApplicationError. Native credentialVersion, proof consumption and transactional policy remain application-owned.

`sessionFacts(now,ttlSeconds,platform,rawSessionOrRefreshCapability,installationCapability,kind='local',allowRebind=false)` returns the selected domain-separated hashes and generated candidate IDs; it has no effects. Include installationCapability in local login bodies and the same fields in OpenAPI. New common `core/auth/session-record.ts` is the neutral session fact type; Principal includes installationGeneration. The selected factory composes these services explicitly through ordinary Nest providers.

The Mongo identity initializer calls three owner functions: `modules/identity/identity-lifecycle-migration.ts:migrateIdentityLifecycle(db)`, `modules/installations/installation-lifecycle-migration.ts:migrateInstallationLifecycle(db)` and `modules/sessions/session-lifecycle-migration.ts:migrateSessionLifecycle(db)`. They receive the already connected native MongoDatabase; initializeIdentityDatabase owns the identity release locks and completion markers. New provider-cleanup collection/indexes are declared by providerCleanupSchema. Existing sessions without generation facts are revoked during migration, preserving identity/account records and requiring reauthentication with newly domain-separated capabilities. Existing installations without possession hashes cannot be recovered by supplied IDs. PostgreSQL002 makes the corresponding preserving changes and revokes legacy installations' sessions. Session/capability tombstones must be retained: purging them would remove the never-reactivate guarantee.

Both-mode new identity composition uses `FreshIdentityProof(tx,accounts,identities,installations,sessions,passwords|null,firebase|null,methods,recentAuthMs)`, `AccountLifecycle(tx,accounts,identities,sessions,fresh,cleanup|null)` and `InstallationLifecycle(tx,installations,sessions,fresh)`. The selected identity module registers their injectable values and `SelfAccountController` / `InstallationLifecycleController`. Firebase additionally composes native `ProviderCleanupService(db)`, `ProviderLinks(tx,identities,sessions,fresh,firebase,cleanup,projectId,methods,recentAuthMs)` / `ProviderLinksController`, and `ProviderCleanupDispatcher(tx,identities,cleanup,firebase,clock?)`. `FirebaseTokenVerifier` implements cleanup and a purpose-specific `actionLinksAuth()` for mail composition. No local profile imports Firebase SDKs.

`ProviderCleanupDispatcher.drain(limit=10)` accepts1–20 and runs serially, at most8 attempts per intent with exponential backoff capped1hour, a30second claim and10second provider-result deadline. A timed-out SDK call may still be in flight. Delete/revoke intents may retry only against the permanently inactive exact-generation subject tombstone; its ownership can never be rebound. Unknown/inflight unlink keeps its fence across restart and is never automatically retried, because a delayed unlink could otherwise remove a newly linked method. Existing authorized sibling sessions remain usable. An explicit disable/delete is still allowed while unlink is pending, atomically supersedes its binding generation and permanently revokes application authority. Exhausted/unknown intents need restricted operator investigation; there is no public force-reset or subject-rebind path. Ordinary session revocation never enters this dispatcher.

POST `/api/identity/firebase/providers/link` requires `{confirm:'link',idToken,targetIdToken}`; both current actor proof and target subject ownership are verified, recent and project/method constrained. Existing foreign/tombstoned subjects cannot be linked; email is never an ownership key. For same-subject Firebase SDK linking, call the SDK link operation and sync its newly verified provider facts. POST `.../unlink` additionally requires `method` and `confirm:'unlink'`; app authority removes that method before staging the provider effect. Removing the last recoverable method is denied. Unverified email/password alone is not accepted as a recovery anchor; a different password-only binding also cannot establish recovery without a current proof of its verified mailbox. SDK errors never cause a silent account merge.

Both profiles expose POST `/api/accounts/me/disable` or `/delete` with the matching literal `confirm` and the selected fresh proof (`password` or `idToken`). POST `/api/identity/installations/rotate` takes `confirm:'rotate-installation'`, selected fresh proof and old/new installation capabilities. Rotation revokes prior-generation sessions and requires fresh login/bootstrap. Persist the candidate new capability privately before requesting rotation so an uncertain response can recover using fresh authentication; do not fall back to ID-only possession.

For selected reliable local actions, `ActionTokens` accepts optional seventh `ActionDeliveryWriter` and eighth `deliveryLifetimeMs` (default15minutes). It prepares encrypted mail once before the retryable transaction, then stages that identical usable action beside its hash using the exact context. Pass the configured mail maximum lifetime to bound retained mail separately from token lifetime (verification24hours, reset15minutes). Immediate `MailService.submit` behavior remains one attempt after commit and reports real typed outcomes. Durable staging returns no invented provider acceptance.

Only Firebase application action delivery includes `FirebaseActions(tx,fresh,firebase,links,delivery,continueUrl,deliveryLifetimeMs=900000)` and `FirebaseActionsController`. The configured continueUrl is server-owned and checked by M's allowlist helper; clients cannot supply arbitrary continuations. Verification requires the current subject's recent verified identity and its real provider email; phone-only identities are suppressed. Reset uses enumeration-safe responses and the same availability boundary for suppressed subjects. Both call M's Firebase link helper and durable writer; neither calls local password/action routes. Provider-managed mode emits only the provider-managed client/helper selected by M.

Client assets are `clients/auth-local.mjs` and `clients/auth-firebase.mjs`. Local shared-tab sessions require one shared private store plus Web Locks/equivalent mutex; independent instances observe a completed refresh before deciding to send, and uncertain refresh responses clear only that app session and require reauthentication. Firebase persists one intended enrollment capability before its first request, serializes concurrent bootstrap, retains it across ID-token refresh/lost responses and uses a separate device capability. After revocation, explicitly reauthenticate and begin a new intended session; never retry a revoked enrollment as new. Examples implement all four SDK method entry points, linking/unlinking, self actions, installation rotation and selected action requests. Real SDK/phone/Google/Apple/native credential and action-handler acceptance remains external.

Application code must recheck the current principal's exact installation generation before delayed disclosure or effects. A bearer guard cannot retract bytes already sent or an external effect already accepted; atomic application writes should validate current authority in their own explicit transaction. Push and realtime owners consume the neutral Principal generation fact rather than importing identity models.

For a protected route in a custom feature, explicitly pass `capabilities.auth` from `AppCustomModule.register` into that feature's Nest module imports. The configured identity module exports the existing `HttpSecurityModule`, so the feature can use `PrincipalGuard` and `CurrentPrincipal` with the selected authority.

## Client setup and private storage

For local auth, construct `LocalAuthClient({origin,store,locks,lockName})` after providing a private asynchronous store with read/write and a mutex shared by every client instance/tab using that store. Browser Web Locks is the default mutex; unsupported hosts must supply an equivalent. Store device possession separately from the rotating refresh session. Select a distinct lockName for each independent session store. Registration does not log in; the email-proof holder chooses a new password at confirmation, then explicitly logs in. Reset and password change invalidate old families. Never retry an ambiguous refresh, and never share one family across tabs without the shared mutex/store. The example supplies safe session lists, all four revoke scopes, fresh self actions and installation rotation. Non-current session scopes require recent application-session authentication; use an independent fresh login when the existing enrollment is old.

For Firebase, pass the real modular client SDK exports, configured Auth, API origin and one private enrollment store per intended app session to `FirebaseAuthClient`. Do not point multiple independent tabs at the same enrollment store. They may use the same Firebase project/user and still enroll separate independently revocable API sessions. Backend identity Firebase project/ADC is separate from optional FCM project/credentials. Enable only selected methods and configure each external method:

| Method         | Client entry and required external setup                                                                                                                                                                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email/password | Enable Firebase email/password; `emailPassword(email,password)` uses signInWithEmailAndPassword. Configure authorized action domains and selected provider/application delivery; never send the Firebase password to local credential endpoints.                                                                                |
| Phone          | Enable phone auth, authorized web domains and reCAPTCHA/application verification; `phone(number,recaptchaVerifier)` returns the SDK confirmation, then call confirmation.confirm(code) before bootstrap. Android/iOS verification credentials and actual SMS evidence are external. A phone-only subject has no invented email. |
| Google         | Enable Google and authorized origins/redirect domains; `google()` uses GoogleAuthProvider/signInWithPopup. Native clients require their matching OAuth client/SHA/project setup. Generate installation possession once with createPrivateCapability(), retain it privately, and generate a different session capability for every explicitly new intended API session. FirebaseAuthClient bootstrap persists/reuses its session capability automatically; beginNewSession(reauthenticate) explicitly replaces a revoked or expired enrollment only after recent SDK authentication. Existing successful enrollment survives ordinary SDK token refresh. Use private device/OS storage on native clients; web store implementations must be scoped to the intended session and protected from analytics/third-party access. These examples accept a store capability and do not silently persist secrets in localStorage or URLs.

Firebase provider linking uses real SDK linkWithCredential or linkWithPopup plus a UI-supplied reauthentication callback, then syncs verified provider facts with the backend. Google/Apple popup linking passes the corresponding configured provider; email/password uses EmailAuthProvider.credential, and phone uses the actual confirmed phone credential. Unlink asks the backend first so last-method and durable-intent policy is enforced before Admin cleanup. Provider-managed actions/handlers use selected `mail-firebase-actions.mjs`; application delivery uses this client's explicitly named application request methods only when that mode was selected. Both handlers stay on Firebase SDK action-code APIs and validate configured continuations through M's asset. No Firebase emulator/provider fake is a production client flow.

## Selected runtime factories and trusted provider seam

The generator fixes the auth/database/action mode once; no environment or HTTP input selects a replacement provider. The local factory is `createIdentityRuntime(config, db, mail: MailSubmitter, delivery?: ActionDeliveryWriter)`. It constructs JoseAccessTokens from **config.auth.jwtPolicy**, never from a UTF8 JWT_SECRET. Selected reliable local output requires the writer and passes **config.mailDelivery.maxLifetimeMs** into ActionTokens; immediate output rejects an unexpected writer rather than silently becoming a different delivery mode.

Firebase provider mode exports `createIdentityRuntime(config, db, dependencies?: IdentityRuntimeDependencies)`. Firebase application delivery exports `createIdentityRuntime(config, db, delivery: ActionDeliveryWriter, dependencies?: IdentityRuntimeDependencies)` and constructs M's FirebaseActionLinksService from the provider's actionLinksAuth() plus **config.firebaseActions.policy/applicationName**; FirebaseActions receives **continueUrl/deliveryLifetimeMs**. Provider mode emits neither application action services nor mail implementation/dependency. M emits its own neutral contracts and selected mail assets independently.

In Firebase output the trusted programmatic dependency is:

```ts
type IdentityRuntimeDependencies = Readonly<{
  firebase?: FirebaseIdentityProvider;
}>;
type FirebaseIdentityProvider = FirebaseVerifier &
  FirebaseCleanup & {
    close(): Promise<void>;
    // Required only in the selected application-action output:
    actionLinksAuth(): Pick<
      Auth,
      'generateEmailVerificationLink' | 'generatePasswordResetLink'
    >;
  };
```

FirebaseVerifier supplies verify(idToken) and assertCurrent(identityKey, authenticatedAt, method?). FirebaseCleanup supplies cleanup(identityKey, 'revoke'|'delete'|'unlink', method). Application-action providers return the exact Admin method subset; no SDK type cast is needed for controlled fakes. The default is the actual configured FirebaseTokenVerifier. Tests may supply a complete synthetic provider through createApp's trusted identity dependency forwarding; there is no emulator environment flag, token bypass route, locator or dynamic provider loader. The returned runtime owns close() for either supplied or default provider, calls it once across concurrent/repeated close requests, and closes after composition failure. Test providers should therefore supply a real cleanup/close implementation for the resources they own.

All factories preserve `{authority,module,close}`. Firebase also deliberately exposes `cleanup: ProviderCleanupDispatcher` for an application-owned bounded drain command. FreshIdentityProof, AccountLifecycle and InstallationLifecycle are normal exported Nest providers; Firebase adds ProviderLinks and ProviderCleanupDispatcher. Owner account/installation/session modules continue to export their own directly injectable services, requiring explicit imports in consumers. New source remains scaffold-owned; selected module composition is managed. Only clients/auth-local.mjs or clients/auth-firebase.mjs is emitted for the selected mode.

## Explicit schema release and neutral observation

PostgreSQL identity initialization holds the existing advisory transaction lock, applies each missing migration in order, and records its marker only after its SQL succeeds; both migrations/markers share the same native transaction. Repeated initialization skips completed migrations. Mongo uses durable identity-v1 and identity-lifecycle-v2 claims, creates base collections/indexes, calls all three owner contributions and marks lifecycle completion last. An interrupted Mongo claim remains incomplete and requires operator reconciliation rather than automatic destructive retry. Existing identity/account data is retained; legacy bearer sessions require reauthentication as described above.

`openDatabase(config, requireInitialized = true, observation?)` forwards to the selected `NativeDatabase.connect(url, requireInitialized, observation?)`. False skips only completed-marker validation; it never initializes schemas. True requires both identity-v1 and identity-lifecycle-v2. The optional neutral interface in the selected transaction-context.ts is:

```ts
interface DatabaseObservation {
  observe<T>(
    operation: 'connect' | 'transaction' | 'close',
    work: () => Promise<T>,
  ): Promise<T>;
}
```

Connect wraps the complete connection/marker check once, and run wraps the unchanged private native retry loop once. The observer therefore sees one terminal transaction outcome after all retries, not one for every attempt. Opaque participant contexts, callback execution and failure mapping remain unchanged. Close caches one observed promise including failure, so concurrent or repeated closes do not repeat the native close or terminal observation. Core imports no diagnostics feature and sends no SQL/parameters to this capability; root may compose the trusted DatabaseDiagnosticsService, which records only allowed operation/outcome/duration facts and preserves the exact native thrown error.
