# Selected service plans and operation artifacts

O0 supplies finite service plans, delegated local execution and distinct Dokploy, Coolify and CapRover artifact profiles. It does not authenticate to a platform, provision a resource, build an image or claim deployed acceptance. Root owns command/catalog/config/package integration and serial generated-image/native-service checks. Reference applications remain unchanged historical inputs.

Service/dev API planning results contain service names, fixed metadata, internal execution vectors and finite status, never private environments or native command output. Their `dryRun` does not inspect the project, probe a port, create a lock or run a command. The command layer reads ordinary desired/realized metadata, validates selected recipes and managed hashes and renders portable summaries; it never serializes internal executable/project-directory paths. Dry CLI commands do not read execution environment values or private file content. No custom error schema is introduced.

`ServicePlanOptions` accepts `environment` (`development`, `test`, `staging`, `production`), exact `targetVersion`, `topology` (`single`, `cluster`), bounded `replicas`, optional `cgroupParent`, opaque `externalResources` and `requireExternalResources`. Defaults are local/development or selected target/production. Only a target's reviewed exact artifact contract version is accepted. Opaque external IDs use bounded identifier characters; URLs, credentials, paths and unselected resource IDs fail. Artifact preview may report unresolved external setup; deliberately requiring a realized plan rejects missing IDs.

Single topology has one replica. Cluster defaults to two and permits at most eight. Selected realtime `scale` must agree with the plan, and native-ws rejects cluster. Cluster requires a shared selected native DB and rejects selected storage/evidence profiles while current application boot constructs local private roots. Socket.IO cluster fanout uses the selected native DB adapter. Centrifugo cluster additionally needs private Redis >=6.2 for its engine, configured independently from auth rate limiting. Dokploy/Coolify standard Compose replicas share a Docker host. CapRover uses native Swarm placement. `serviceFiles` preserves a selected cluster and describes its shared external DB.

## Selected closure and ownership

The plan contains only selected services. Auth contributes the external `auth-redis` resource for short-lived counters and publishes the setting name `REDIS_URL`. The selected Centrifugo cluster engine has a separate `redis` resource. The plan records ports and visibility, dependency IDs, resource caps, health scope, stable resource IDs, environment and secret names, ingress and operator scheduling. Optional Vector/Logdy remain explicitly invoked native tools with owner configuration. The restricted diagnostic reader requires its own private process, profile and TLS setup.

API private volumes are `app-storage` at `/app/var/storage` and `app-evidence` at `/app/var/evidence`, owned by node uid/gid 1000, mode 0700. Local database volume is separate and database-owned. Stable resource names include project and selected environment; ordinary up/down does not regenerate credentials or replace volume identity. Same-user evidence supports one publisher per source root. No shared retained-evidence volume is advertised for replicas. AWS presigned-only does not automatically establish shared runtime roots or cluster acceptance.

Selected external providers appear as explicit nonsecret requirements: native DB, AWS/R2, Firebase, SMTP/Resend, FCM/APNs, Centrifugo/Redis or restricted diagnostic reader. No SDK for another provider/database is introduced. R owns `ops/centrifugo/**` and its selected v6.10.3 descriptor/config; D owns `ops/diagnostics/**`; O0 does not rewrite either asset family. Centrifugo's client WebSocket is public on 8000, authenticated server API and health are private on 9000, and authenticated connect/refresh callbacks are private API routes. Socket.IO's selected WebSocket-only transport needs no polling affinity. Cluster engine/adapter/proxy behavior remains independently tested by root.

Release is `node dist/initialize-database.js` (`release:apply`/`db:initialize`) and uses O1's coordinated native lock/history. The API never applies migrations on boot. Reliable mail is `node dist/drain-mail.js --limit 20`, bounded by CAS/lease and explicitly scheduled. No invented permanent worker exists. Firebase provider cleanup remains an owner dispatcher until a corresponding entry command is selected. Media/push cleanup/delivery is not silently promoted into another worker daemon.

Backup/create and restore commands run on an operator host with matching native `pg_dump`/`pg_restore` or `mongodump`/`mongorestore` tools, plus owner-only `VCLI_BACKUP_PROFILE`/`VCLI_RESTORE_PROFILE`. The Node API image retains compiled `dist/release` and migrations but does not contain those native tools or private profiles. Root separately verifies dump/restore consistency, fencing, media coverage and isolated destinations.

## Environment and container artifacts

The central `EnvironmentContribution` model remains authoritative. O0 preserves required/default/secret metadata, refuses secret defaults and sorts fields deterministically. Required settings reference `${KEY:?message}`; nonsecret safe defaults use `${KEY:-default}`. Optional no-default settings use Compose bare/null entries, which omit absent environment variables instead of demanding empty secret strings. Add them explicitly to target environment settings when used. Selected application configuration normalizes optional blank SMTP/credential-path input.

Selected auth makes `REDIS_URL` a required private deployment setting. The Redis endpoint must be reachable from the API, and all replicas in the same environment use the same endpoint. Bind it with `--resource auth-redis=<resource-id>` when planning a deployment. A selected Centrifugo cluster engine uses `--resource redis=<resource-id>` and `CENTRIFUGO_ENGINE_REDIS_ADDRESS`. Set runtime secrets through the deployment environment or an explicit private `APP_ENV_FILE`. Process variables override the file. Planning and deployment artifacts expose setting names. Staging uses `NODE_ENV=production` with distinct resources and secrets. Production capture is rejected. Review `PUBLIC_ORIGIN`, `ALLOWED_ORIGINS` and the selected mail sender settings. [Deployment operator inputs](CLI-DEPLOYMENT-OPERATORS.md)

Selected SDKs can also use `GOOGLE_APPLICATION_CREDENTIALS` for Firebase/FCM, or `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_SHARED_CREDENTIALS_FILE` and `AWS_PROFILE` for AWS/R2. Workload identity may supply credentials instead.

`ops/Dockerfile` uses `node:26.13.1-bookworm-slim`, a reviewed committed install-links lock and `npm ci --install-links`; this copies the genuine selected `tools/vcli-auth-runtime` file dependency into production node_modules. Build runs ordinary selected Nest scripts. Its only build argument is nonsecret `VCLI_SOURCE_COMMIT`, an explicitly reviewed 40-hex source identity supplied by CI; when nonempty, the build invokes `scripts/write-build-metadata.mjs --source-commit` after compilation and retains the writer output in final dist. Runtime environment cannot replace that identity; missing identity stays null and deployment verification refuses it. Native operators verify the actual image digest independently. Prune removes private CLI development dependencies; assertions reject a residual CLI or symlinked selected auth runtime. The final image copies package metadata, production node_modules, compiled dist, selected migrations and diagnostic runtime `.mjs` scripts. It contains no private CLI tools directory, contributor path, source tree, dotenv file, credential, runtime-secret build argument or copied operator profile. Only the selected code/dependencies reach application runtime; generator templates remain private development tooling.

Image private roots are created with correct ownership/mode before `USER node`; readiness is narrow `/health/ready`, with SIGTERM and 30-second Compose grace. An empty named-volume copy-up preserves image ownership; an existing bind/root-owned volume requires deliberate operator permission repair. Target volumes are explicitly preprovisioned/reused external volumes. Ordinary down has no `--volumes`, `--rmi` or broad reset.

`compose.yaml` content is deterministic JSON, also valid YAML1.2; the existing formatter may emit equivalent YAML. No YAML parser is invented or installed. Native Docker Compose configuration validates emitted files without starting Docker, pulling images or building. Service execution rechecks the expected raw or approved-formatted owned compose bytes plus the selected JSON metadata; customized artifacts fail rather than being executed or overwritten.

## Local wrapper behavior and evidence boundary

The generated API works with native database and Redis processes. The optional `vcli services` Compose wrapper manages the selected MongoDB 8.0.38 or PostgreSQL 16.16 database. MongoDB uses a development-only unauthenticated replica set on loopback. The wrapper initializes it explicitly and checks for a writable primary. A host API uses `directConnection=true` with the configured loopback port. The PostgreSQL wrapper requires privately supplied `VCLI_POSTGRES_PASSWORD` matching the generated app's `DATABASE_URL`. Retain the password across restarts. Changing the interpolation variable does not rotate an existing database password. Shared cluster databases are external.

Auth-enabled projects can opt in to `vcli init ... --redis-docker`, which adds `ops/compose.redis.development.yml`. Run the following from the app root when choosing Docker for Redis.

```sh
docker compose -f ops/compose.redis.development.yml up -d
docker compose -f ops/compose.redis.development.yml down
```

The Compose service binds `127.0.0.1:6379` with ephemeral counters. `VCLI_REDIS_PORT` overrides the host port for the Compose commands. Set the same port in the app's private `REDIS_URL`. The `vcli services` database wrapper and `vcli dev` leave the optional Redis service to those explicit Compose commands.

Development and test use their matching immutable profile paths, Compose projects, labels and durable volume IDs; test never selects the development aliases. Global project names retain the existing 1–64-character metadata contract. `serviceResourceName` preserves short physical names and, where normalization or a 63-character native limit requires it, derives a bounded prefix plus a deterministic 16-hex SHA256 suffix. Full project identity stays in metadata and labels. A test profile can choose another explicit database port; a port conflict fails rather than selecting another environment’s data.

`VCLI_DATABASE_PORT`/`databasePort` configure only the selected local listener. `VCLI_CGROUP_PARENT`/`cgroupParent` is a host-specific seam; the portable profile hard-codes no host name. Root must supply its current host's required parent (for this contributor VPS, `orca.slice`) and observe the shared memory budget. There is no Docker start/build/pull here. APP_ENV_FILE belongs to the API; Compose disables implicit `.env` loading and uses the explicit execution environment for its own variables.

Service mutation checks the selected artifact and every discovered container's Compose project, project working directory, VCLI project/environment and allowed selected service labels. Before up, a bounded named-volume listing also refuses foreign/unproven ownership; generated volumes carry project/environment and `VCLI_WORKSPACE_ID`, a nonsecret canonical-root SHA256 injected by the wrapper. A per-project environment lock prevents competing local mutations. Existing ownership/stale/edited artifacts, native command failures and invalid ports fail without broad compensation. Status is read-only, creates no lock and returns only service/state; native errors are sanitized. Dev checks the requested loopback port, installed project-local Nest path, private env file and exclusive ownership lock. It never kills a foreign PID or process selected by name/port. A replaced lock is preserved; a stale lock is reported for deliberate reconciliation.

Worker test emission is isolated under ignored `var/cli-operations`; no root/example dist, installs, shared services, Docker startup, image build, provider network, browser or deployment was used. Focused tests include controlled process/runner fixtures and an ephemeral in-process loopback listener with finally cleanup. They are contract evidence, not actual npm/Nest/Docker lifecycle or provider acceptance. Native `docker compose config` and shell/Node syntax checks are read-only parsing evidence. Root separately owns packed installation, production image/auth file dependency, real service/release/HTTP/restart, multi-node and live platform acceptance.

## Operational command integration

`registerOperationalCommands(program, context, execution?)` is registered in root-owned `src/cli.ts` after global/output configuration and before parsing. Context stays `{project(), emit(result), setOperation(name), json()}`; optional execution supplies controlled runners/environment for focused contracts. The registration shape is:

```ts
import { registerOperationalCommands } from './commands/operational-commands.js';

registerOperationalCommands(program, {
  project,
  emit,
  setOperation: (name) => {
    operation = name;
  },
  json: () => !!program.opts<GlobalOptions>().json,
});
```

The helper registers `services plan|up|down|status`, `dev` and `release apply|reconcile|backup|restore`. Services accept `--environment development|test`, `--database-port`, `--cgroup-parent` and `--dry-run`. Dev accepts the same local environments, `--port`, `--config-file` and `--dry-run`. It uses `--config-file`, then `APP_ENV_FILE`, then an existing `.env.<environment>`. Start dependencies, apply the schema and install packages explicitly. Use VCLI's `--config-file` because Node reserves `--env-file`. A dry run previews the selection without reading private config. Actual runs check that the selected file is owner-only. Actual dev streams the local Nest compiler. `--json --dry-run` returns the portable preview. Private execution values stay outside CLI results.

For a freshly generated database profile, start the selected native database and, for auth-enabled projects, start Redis. Edit the generated mode `0600` `.env.development` if local connections differ or the selection needs provider settings. Run `make first-run` to build, apply the schema release with that file, and start the watcher. To run the steps separately, use the same file with `vcli config check --config-file .env.development`, `npm run build`, `vcli release apply --config-file .env.development`, and `vcli dev --config-file .env.development`, in that order. Supply a separate private profile for testing.

`vcli config check` loads the file with the project's `loadSelectedEnvFile` and `loadConfig`. Process variables take precedence. The check reports invalid setting names and validates configuration without checking service connectivity. A dry run leaves the file unread. If the project has no startup module, check returns `schema-unavailable`. `vcli doctor` stays read-only and reports `configValidation.status` `not-run`. `vcli logs status` and `vcli logs query --request-id <uuid>` read the retained diagnostic files after a build. `vcli explain <path>` names the owner and a focused check. `vcli check --only <name>` runs one declared script and leaves the recorded full-check outcome unchanged. Default text output is a compact summary. `--verbose` prints the full JSON data.

Existing engine read/inspection helpers reject desired/realized drift, incomplete source, unsafe paths or changed managed output. Source-only service setup is permitted, with incomplete installation/check outcomes visible. Actual dev/release require healthy recorded installation; previews do not. An ordinary operation never marks installation/check outcomes complete. Changed managed scripts, unsupported input/environment, stale local profiles and missing selected DB fail before delegation. Missing test profiles cannot fall back to development or silently regenerate files.

Release actions map only to managed `release:apply`, `release:reconcile`, `backup:create`, `backup:restore` scripts and verify their exact recorded Node targets. They delegate `npm run --ignore-scripts <script>` through an argument vector; [npm documents](https://docs.npmjs.com/cli/v11/commands/npm-run/#ignore-scripts) that this executes the named script while skipping pre/post hooks. Profile/decision contents are never read by the CLI helper: actual `--profile` or `--decision` is permission-checked and passed privately as `VCLI_BACKUP_PROFILE`, `VCLI_RESTORE_PROFILE` or `VCLI_RELEASE_DECISION`, with explicit matching environment values also supported. Dry release output contains only script and existing source/install/check outcomes. Actual release parses one allowlisted JSON object from the managed script and returns that result in the fixed envelope. Raw child output is not published. Config failure, a completed release and an ambiguous write name different next commands. Native backup tooling remains operator-host scope.
