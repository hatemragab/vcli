# VCLI developer and AI agent review

19 November 2026 · Installed VCLI 0.1.1 · Node 26.13.1 · `examples/test_notes_mongo`

The biggest improvement is to carry the first failure, its location and the next useful command through VCLI. Today a failed check or startup can leave an agent searching the project again for facts the tool already had. The generated Nest application already has a readable controller, service and entity layout. Keep that layout and improve the command and diagnostic boundaries around it.

The review covers init, add, scaffolding, planning, install/check, inspect/doctor, local services, release, recovery, maintenance and deploy interfaces, along with generated source, runtime logs, packaging and test navigation. Evidence comes from current source, installed help and dry runs, the generated project, and independent read-only reviews. Runtime services, live targets and provider integrations were outside this review.

## Findings

### 1. P1 · The documented dev flag can fail before VCLI starts

**Reproduced.** In the generated project, `vcli --json dev --dry-run --env-file .env.development` exits 9 with Node's file-not-found error and no VCLI JSON. The same dry run without that flag returns a preview. Node recognizes its own option before Commander receives the arguments. This also prevents VCLI from enforcing its intended distinction between preview and actual environment-file handling. The command in the previous walkthrough needs correction. [Flag registration](../src/commands/operational-commands.ts#L346) · [Dev preview and file validation](../src/services/dev-command.ts#L77)

Use `--config-file` for the VCLI option and test the actual installed executable with a missing file in dry-run mode. Keep the existing `APP_ENV_FILE` fallback. The verified immediate workaround for preview is `node -- node_modules/@vcli/cli/bin/vcli.mjs --json dev --dry-run --env-file .env.development`.

### 2. P2 · Install, check and release lose the useful part of a failure

**Source confirmed.** The package runner discards child output and retains only the exit code. A check failure records the step internally, then throws a generic `CHECK_FAILED`. Install catches phase-specific errors and returns one `INSTALL_FAILED`, so npm resolution, the root lifecycle hook and post-install verification can look identical. Release discards even the managed script's successful release ID and owner summary. The release script itself collapses configuration and owner failures into one reconciliation message. [Runner](../src/commands/package-runner.ts#L14) · [Install](../src/engine/execution.ts#L242) · [Checks](../src/engine/execution.ts#L309) · [Release delegation](../src/commands/operational-commands.ts#L492) · [Release entry point](../src/recipes/render-schema.ts#L202)

Keep one JSON result on stdout. Add bounded fields for the failed step, known script, exit code or signal, source/install/check outcomes and the existing operation ID when one exists. Give the agent the exact focused rerun command. For checks with structured output, emit approved relative file paths, line numbers and diagnostic codes. Share one allowlisted result format with the managed release scripts so config failures, completed releases and ambiguous writes have different next actions. A small last-result record can hold these facts separately from the recovery journal.

### 3. P2 · Doctor can report success while the app still needs setup

**Reproduced.** `vcli --json --project examples/test_notes_mongo doctor` completed with zero issues while the project had only env examples and blank JWT settings in those examples. This is consistent with the current metadata check. The result does not say whether runtime config was validated. The generated config parser can identify invalid keys, but startup collapses config, connection, schema and Nest failures to `STARTUP_FAILED`. A listen failure after composition enters cleanup without a primary startup error event from `main.ts`. [Doctor](../src/engine/inspection.ts#L318) · [Selected config parser](../src/recipes/render-config.ts#L511) · [Generated startup](../examples/test_notes_mongo/src/main.ts#L5) · [Composition failure handling](../src/recipes/render-composition.ts#L132)

Keep the default doctor read-only and add an explicit config check that uses the same selected schema as startup. Report missing or invalid variable names, config validation status and the next command. Add finite startup stages for config, database connect, schema release, module initialization and listen. Separate deterministic startup guidance from recovery decisions. For this profile the first-run recipe should put MongoDB startup, private JWT configuration, release, readiness and Swagger in execution order using the same configuration file for release and dev.

A compiled-config probe also confirmed that `EVIDENCE_MAX_BYTES=1` passes configuration and is rejected by the diagnostic reader, which requires at least 512 bytes. Share that bound with the config schema so this case names the affected key before initialization. [Generated config bound](../examples/test_notes_mongo/src/core/config/load-config.ts#L64) · [Reader bound](../examples/test_notes_mongo/src/modules/diagnostics/diagnostic-reader.service.ts#L86)

### 4. P2 · Existing logs are hard to query from the terminal

**Source confirmed.** The generated app sends `X-Request-Id`, records safe HTTP failure facts, and includes a bounded retained reader when local diagnostics is selected. This profile has application, database and infrastructure evidence but has no direct CLI query command. A developer looking up a failed request has to find and inspect the rotated evidence files. [Request correlation](../examples/test_notes_mongo/src/core/http/record-request.ts#L11) · [HTTP error filter](../examples/test_notes_mongo/src/core/http/http-error.filter.ts#L34) · [Selected diagnostics](../src/recipes/render-diagnostics.ts#L10)

Add a thin `vcli logs` entry point around the existing reader. Start with status and a bounded query by request ID or operation ID. Keep reader limits, pagination and gap/drop status visible. If a valid public request fails input validation, include safe known field names and a stable validation code in the response where useful. Keep request values and credentials out of both responses and evidence. The operator can already use the request ID header, so the first pass needs no new collector, server or transport.

Search results also need consistent tags. The route allowlist omits generated paths such as media upload reconciliation. The application returns codes such as `MEDIA_GENERATION_CONFLICT` that the current filter can log as `INVALID_REQUEST`. Derive approved route templates and error codes from a shared owner list, with a bounded fallback for custom routes. [Route schema](../examples/test_notes_mongo/src/core/logging/log-event-schema.ts#L200) · [Media reconciliation](../examples/test_notes_mongo/src/modules/media/media.controller.ts#L302) · [Media error](../examples/test_notes_mongo/src/modules/media/media.service.ts#L125)

### 5. P2 · Generator errors hide the origin of the fix

**Reproduced.** Noninteractive local email auth with MongoDB and no mail returns `INVALID_OPTIONS` from the renderer. The selection rule had already identified mail as the missing capability. By source, template read/format errors, duplicate output paths and missing package pins can reach the same catch. Planning conflicts can also lose the known relative path, even though inspect identifies managed paths. [Selection rule](../src/recipes/selection.ts#L26) · [Render error handling](../src/engine/planning.ts#L101) · [Duplicate output check](../src/recipes/render-project.ts#L185) · [Package import scan](../src/recipes/render-package.ts#L56)

Use a small typed error contract shared by recipes and the engine. Keep a safe code, recipe or option, relative path and actionable hint. Distinguish validation from a broken distribution or template. Guard required template markers before slicing or replacing source. Preserve a stable plan or operation correlation value during apply and recovery. These changes make failures actionable without printing raw compiler buffers, source bytes or arbitrary exception messages.

### 6. P2 · Plans and code searches mix app source with the pinned tool

**Measured.** A minimal installed-CLI JSON init preview listed 527 paths, 477 under `tools/`, and used 59,010 bytes of stdout. The generated notes project records 677 paths, including 477 under `tools/vcli/`, while its `src/` contains 140 TypeScript files. Human output dumps the full JSON, and successful generation returns both the plan changes and the applied paths. The copied CLI is useful for reproducibility, but it makes the first page of an operation and broad code searches noisy. [Distribution copy](../src/distribution.ts#L75) · [Plan summary](../src/engine/planning.ts#L614) · [Result output](../src/commands/command-output.ts#L15)

Default text output to selected features, outcome, operation ID and counts grouped by app, assets and pinned tooling. Keep complete files available explicitly and preserve the existing JSON contract during migration. Add a read-only `vcli explain <path>` that tells the agent the owner, selected template or renderer, and a focused check. Build provenance from render contributions and support older locks with unknown provenance. Avoid editing files beneath `tools/vcli` to fix a generator defect.

### 7. P2 · Help and onboarding send agents to the wrong place

**Reproduced.** A preview of `g feature review-widget --use notes` succeeds while `g --help` omits `notes`. A preview using unselected mail returns a generic recipe hint. Catalog emits IDs and unconditional requirements but no option examples, defaults or conditional dependencies. The architecture guide says init does not exist, START-HERE directs current work back to Phase 00, and several navigation links depend on ignored local artifacts. The notes app's generated docs and OpenAPI describe realtime behavior even though realtime is absent. [Scaffold help](../src/cli.ts#L228) · [Catalog output](../src/cli.ts#L278) · [Onboarding](../START-HERE.md#L32) · [Architecture](ARCHITECTURE.md#L50) · [Notes description](../examples/test_notes_mongo/src/modules/notes/notes.controller.ts#L29)

Use the same scaffold definitions in help and validation. Add per-recipe detail with defaults, prerequisites and valid command examples. Generate README, Swagger and AGENTS guidance from the selected profile. Make the repository entry point a task-to-file-to-check map, and label the planning documents and ignored review artifacts as historical or local.

The local disk profile's controller also registers grant and multipart routes although only mediated uploads are selected. Keep verification and authorization on existing routes, then generate only the selected routes and OpenAPI descriptions so clients and agents can discover what actually works. [Generated media routes](../examples/test_notes_mongo/src/modules/media/media.controller.ts#L215)

### 9. P3 · Make verification scope and preflight cost visible

**Source and timing.** This project's doctor took about three seconds in one local sample. Scaffold calls full inspect and ignores its returned issues, then reads configuration again. Inspect scans managed output, installed payload and journals. The notes app's two generated tests cover readiness state and config error redaction using `dist`. CLI tests also consume `dist`, while the username renderer fixture compiles current source. A passing command is easy to misread when those prerequisites are scattered. [Scaffold entry](../src/cli.ts#L245) · [Inspect](../src/engine/inspection.ts#L224) · [Generated tests](../examples/test_notes_mongo/test/foundation.test.mjs#L3) · [Username rendering fixture](../test/username-rendering.test.ts#L18)

Share the verified project snapshot within a command and keep apply-time checks. Measure before changing any ownership or installation guard. Label test commands with their input and evidence level. Start with the renderer/command fixture for a generator change, the notes runtime test for owner behavior, and the opt-in native journey when a MongoDB claim needs it. Use an installed-bin regression for public flags, since direct command handler tests cannot catch launcher argument handling.

Show selected nonsecret choices in inspect, including the username option behind `auth.local`. Label its check result as the last recorded run; include its time and failed step when available. A focused check could run one declared script while leaving the recorded full-check outcome unchanged. [Inspection result](../src/engine/inspection.ts#L249) · [Profile options](../examples/test_notes_mongo/vcli.json#L7)

## Order of work

1. Fix dev flag parsing and document the exact local setup sequence.
2. Return first-failure details for check, install, render and release. Add one targeted failing fixture per boundary that asserts a usable error and safe output.
3. Add explicit config preflight and request-ID log lookup using the existing schema and retained reader. Exercise the actual generated notes app from startup through a request and verify that the request can be found.
4. Add compact output, per-file provenance and the task-to-file-to-check map. Follow with targeted file splits and common-template deduplication.

A useful acceptance target is that a failed type check, malformed config, failed release or HTTP request each gives the agent a specific next step in its first result. A generated file should have one discoverable owner and a focused verification command.
