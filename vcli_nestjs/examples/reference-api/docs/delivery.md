# Mail and push in the reference application

Current source is MongoDB-only and uses `TEST_DATABASE_URL` for real database fixtures. The [current verification record](VERIFICATION.md) identifies native local acceptance; earlier checkpoint results below remain historical. External provider acceptance remains separate.

This is hand-built reviewable NestJS source, not generated output or completion of VCLI's email/push phase. Capture and fake provider fixtures are local evidence. Hosted SMTP/Firebase/FCM/APNs acceptance, inbox placement and Android/iOS device behavior remain pending until configured and actually exercised.

## Compact modules and direct injection

`mail/mail.module.ts` owns `createMailSender` and `createTestMailCapture`; `MailModule` binds the selected sender under the directly injectable `MailService` class token. Capture and SMTP implement that service without an extra submitting facade. The same sender instance supplied by root remains shared with identity and capability consumers. The capture inspection/clear functions belong only to the explicit test factory closure, never to the injected service or HTTP. There is no debug action-token endpoint.

`push/push.module.ts` owns push composition and exports the directly injectable `PushService`. FCM/APNs implementations, the entity, controller and specialized persistence helper stay in the flat push folder. `PushService` owns purpose selection, bounded dispatch and eligibility checks; the minimal SDK submission shape lives with push types rather than a collection of application ports. `PushRepository` keeps atomic registration, deduplication and generation-guarded removal behind its state store. Generic shared CRUD cannot replace these fenced workflows. Media and push are independent participants composed above them by `createCapabilitiesRuntime` in `media/media.module.ts`; neither storage nor push imports media, even for types.

## Mail contract and private capture

Root creates `createMailSender(config)` once from `src/modules/mail/mail.module.ts`, supplies that exact `MailSubmitter` to identity and capabilities, and exposes no ordinary public send-mail or capture-inspection route. Identity owns action purposes, one-use/expiry policy, anti-enumeration responses and token generation; the selected mail adapter delivers those rendered messages. No additional auth credential is generated on an ambiguous SMTP result.

The shared sender accepts operation identity, one recipient, subject, text, optional HTML and verification/password-reset/notification purpose. This reference deliberately derives HTML from escaped plain text and ignores caller HTML: no arbitrary template path, caller-controlled sender, attachment, URL/file loading or active markup is accepted. Subjects reject newlines, recipient syntax refuses list/header delimiters, and input lengths are bounded. HTML escaping does not make arbitrary continuation URLs safe. `approvedActionUrl` is an origin-allowlisted helper for application-controlled action URLs, rejecting credentials and insecure non-loopback HTTP. Identity owns its local action URL policy; do not accept a caller's arbitrary continuation domain.

`MAIL_DRIVER=capture` is development/test only. It retains at most `MAIL_CAPTURE_MAX` messages (default 100, maximum 1000), at most 1 MiB total, and 15 minutes of bodies. Expired entries are pruned on submit/inspection, oldest entries are evicted first, and process exit releases in-memory state. It does not write an action-link spool to disk. The ordinary factory returns only `submit`, never an inspection property. Tests can explicitly create `createTestMailCapture(maximum, clock)` and own its separate `{sender, inspect, clear}` handle. Keep that handle inside bounded private test context and clear it afterward. Do not place messages, action links or captured tokens in logs, debug routes, diagnostics, evidence or backups. Capture refusal is enforced again at the factory in production.

Submission outcomes are `captured`, provider `accepted`, `rejected`, `unavailable` or `unknown`. Capture is not SMTP. SMTP acceptance is not inbox placement, reading or Firebase authentication. Submission has no automatic retry; callers must preserve operation semantics and treat unknown acceptance conservatively. Message-ID is derived from the same operation ID, but SMTP does not provide an exactly-once or deduplication guarantee.

## SMTP setup

Select `MAIL_DRIVER=smtp`, approved `MAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` and optional paired `SMTP_USER`/`SMTP_PASSWORD`. `secure=true` means TLS on connect (typically port 465); otherwise production requires STARTTLS. Certificate verification and TLS 1.2 minimum stay enabled. Missing host or partial auth configuration is rejected. No insecure certificate bypass is exposed. Nodemailer disables file/URL access, protocol debugging and raw logging. Connections, greeting and socket timeouts are 5/5/10 seconds, at most four active submissions per process, one recipient per action.

Explicit SMTP 4xx and 5xx map to unavailable/rejected. A connection-stage failure is unavailable; a timeout/disconnect after possible DATA submission is unknown. Authentication/TLS configuration errors do not masquerade as successful delivery. There is no durable mail outbox or campaign system in this reference. If later workflows need durable secret-bearing action jobs, design encrypted minimal retention and recovery before adding a queue; the in-memory capture is not such a store.

The operator must authorize/configure an SMTP relay, sender/domain, SPF/DKIM/DMARC, TLS trust and Apple private relay sender requirements where relevant. No relay account is provisioned here. `REFERENCE_TEST_SMTP=true node --test test/delivery-smtp.test.ts` runs a test-owned loopback SMTP protocol peer to exercise actual Nodemailer acceptance/rejection. The coordinator's successful local protocol run is recorded in the [verification record](VERIFICATION.md); it does not establish hosted relay or inbox delivery.

Firebase-managed action mail leaves generation/delivery with Firebase's supported flow. The Admin-generated, application-delivered Firebase action-link workflow is not implemented or exposed by this reference and remains pending, as documented in [identity](identity.md). `MailSubmitter` can carry rendered links but does not supply that integration. Local authentication uses its own action credentials. SMTP does not replace Firebase authentication, phone verification, OAuth provider configuration or mobile action handling. Real Firebase action/link-domain, expired/used links, provider console and client continuation checks need separate evidence.

## Push registration and HTTP routes

All push HTTP routes import the shared security module and require current principal authority. Destination ownership is derived from that account/session/installation, never from body owner fields. A push token is not proof of physical device identity.

OpenAPI supplies explicit registration, generation-fenced removal and self-notification request schemas, UUID parameters, bearer authentication and the optional Firebase session-secret header so Swagger can submit the supported inputs. The self-notification schema advertises ordinary/background only; its generic review route refuses VoIP calls.

| Endpoint                            | Contract                                                                                                                                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/push/destinations`       | Strict JSON fields: `purpose` is `ordinary`, `background` or `voip`; `platform` is `android`, `ios` or `web`; `token` is the provider token. Registers/rotates this authenticated installation's destination and returns only a safe projection.                    |
| `GET /api/push/destinations`        | This account's current installation projections, excluding tokens, hashes and session secrets.                                                                                                                                                                      |
| `DELETE /api/push/destinations/:id` | Body `{generation}`; exact account/installation/ID/generation fencing prevents stale removal.                                                                                                                                                                       |
| `POST /api/push/self`               | Bounded ordinary/background review notification to this installation only: `{purpose,title?,body?,data?,ttlSeconds?}`. No arbitrary account/token target. Ordinary requires an alert; background forbids one. VoIP through this generic review endpoint is refused. |

Trusted application modules import `PushModule` and inject `PushService` from `push/push.service.ts` for account/installation delivery after authorizing a real business event. The old dispatcher token/port and routing wrapper are removed; purpose routing runs in `PushService` with selected SDK senders. Direct APNs VoIP is implemented there and requires an authorized real call plus `data.callId`; the generic self-test cannot invent a call. There is no unauthenticated or arbitrary-recipient send endpoint. Payloads should contain opaque references, not sensitive account data; clients fetch content through authenticated APIs.

When FCM is enabled it is the ordinary route. Otherwise configured APNs supplies ordinary push. APNs supplies explicit background and VoIP purposes; FCM ordinary plus APNs VoIP may coexist without duplicate ordinary routing. Missing purpose/provider configuration fails explicitly. Local JWT authentication can use FCM independently: set `FCM_ENABLED=true`, `FIREBASE_PROJECT_ID` and Firebase application-default credentials even with `AUTH_DRIVER=local`.

## Push persistence and fencing

The push owner stores secret tokens in its own `reference_push_state` MongoDB collection, separate from identity schemas. It uses a bounded global reference aggregate (1024 destinations total, 32 per account) with MongoDB revision-guarded atomic replacement. Atomic registration deduplicates provider/scope/token ownership and replaces the same installation/purpose/scope; a changed account clears the installation's previous-account purposes in that scope. Ordinary/background references may share a token on the same installation/account. A token already bound to a different installation is refused rather than silently stolen. APNs tokens use canonical lowercase hexadecimal without spaces/brackets. The state store validates and explicitly maps stored MongoDB Mixed records before application use. This bounded aggregate is a deliberate prototype capacity; a larger production catalog needs reviewed indexed records/transactions rather than removing bounds.

Records include account/session/installation, app/environment/provider scope, purpose/platform, token and generation. Each registration creates a new ID/generation. Dispatch snapshots retain their exact account binding and generation. Before each provider call/retry, current authority and current destination generation are checked. Logout/revocation makes the recorded session ineligible; the client should unregister before logout, then re-register on its next session/account binding. Store-level binding changes never redirect prior-account queued work to a new owner. The current reference ties eligibility to the registering session; a sibling session alone does not keep that record eligible after the registering session is revoked. Each login/bootstrap creates a fresh installation; stable reuse and cross-account installation rebind are not exposed. Reclaiming a token after losing its old binding needs a separate design; see the [identity limits](identity.md).

Provider invalid-token cleanup deletes only the exact account/installation/ID/generation. A late result cannot prune a rotated/rebound destination. Credential, payload and connectivity failures never remove tokens. APNs `Unregistered` cleanup additionally requires its invalidation timestamp to be at least the registration time; a wrong-environment `BadDeviceToken` is not treated as definitive invalidation. Token values/hashes are never returned in projections or logged. Restrict database credentials, use appropriate disk/provider encryption and protect backup access: tokens are usable secret destinations, not hashes alone.

Scope includes environment, public application origin, Firebase project, APNs topic and sandbox/production selection. Changed provider scope requires re-registration; old records are ineligible rather than reinterpreted with new credentials. Memory state is non-production and does not prove persistence.

Dispatch allows four concurrent operations, at most 32 selected destinations per operation and at most three attempts for explicit retryable failures. Backoff is bounded, honors expiry and stops when the provider requests a delay above two seconds. Long throttles return unavailable for the caller to schedule later; unknown acceptance is never retried automatically. FCM SDK work remains counted against its four-call cap until it settles even if the ten-second caller deadline returns unknown. There is no durable push queue, cross-process rate limiter or exactly-once delivery guarantee. Revocation/rotation can race an already-started provider call; bytes accepted by a provider cannot be recalled.

## FCM setup and outcomes

Enable the project's Cloud Messaging API and authorize a least-privilege service identity through the Admin SDK credential chain. Configure Android package/signing, iOS APNs credentials/capabilities and browser service worker/VAPID/permission settings separately. Firebase identity provider selection is unrelated to FCM routing. The pinned Firebase Admin SDK handles signing/transport. The adapter sends one destination at a time, bounds the payload, sets expiry/TTL and translates acceptance into a provider message reference. Only exact unregistered/invalid-registration errors justify cleanup; invalid payload or mismatched credentials do not. Quota/throttle is unavailable, ambiguous transport failure is unknown. No FCM/device acceptance is claimed without an authorized project and client.

## APNs setup and outcomes

Set `APNS_ENABLED=true`, team/key IDs, `APNS_KEY_PATH`, the base bundle topic in `APNS_TOPIC` and explicit `APNS_PRODUCTION`. The `.p8` PKCS8 key must be an ordinary private file with mode `0600`/`0400`, at most 16 KiB; never commit it. Its scoped Apple team/app authorization is an operator task. The pinned `jose` library imports/signs ES256 provider tokens; Node's maintained TLS HTTP/2 client handles framing/connection mechanics. Tokens are cached for at most 50 minutes. Certificate validation/TLS 1.2 remain enabled, each request/response is bounded, and connections close after each submission.

Ordinary, background and VoIP use explicit alert/background/voip headers, appropriate priority, app topic or `.voip` suffix, expiry and UUID operation ID. Background is data-only at priority 5; VoIP is a real call path at priority 10 with no stored delivery (`apns-expiration=0`). Ordinary payloads are at most 4096 bytes and VoIP at most 5120; HTTP review inputs are more restrictive. Apple status/reason, throttling and invalidation are mapped per destination without raw provider text. APNs acceptance means provider acceptance, not OS display. Authorized iOS app entitlements, PushKit/CallKit handling, sandbox/production tokens, foreground/background behavior and real call semantics all need physical-device acceptance.

## Operation correlation

`POST /push/self` uses the server-generated `X-Operation-Id` for its response body, provider submission payload and shared HTTP operation logs. Client-supplied operation headers do not select that identity. A terminal HTTP success event records the HTTP boundary; inspect the returned provider outcomes separately and do not interpret it as device delivery.
