# MongoDB repository contract

This expected-output app is initialized for MongoDB/Mongoose only. The independent PostgreSQL example has its own implementation; application source never imports it. VCLI remains unimplemented. `BaseRepository<T extends RepositoryEntity>` holds a protected `Model<T & { _id: string }>` and the selected `MongoDatabase`; feature services inherit it and export their deliberate Nest capabilities normally.

The constructor is `protected constructor(database: MongoDatabase, modelName: string, schema: Schema<T>, duplicateCode?: string)`. Each schema declares string `_id` and public `id`. Creation stores both with the same value, public `id` is immutable, and read/update/delete predicates on `id` are mapped to indexed `_id`, including `$and`, `$or` and `$nor` branches. Public-ID sort and distinct access also use the indexed primary key. Other ownership predicates are retained. Supplying both ID forms in one predicate is rejected. Default results omit internal `_id`, `revision` and version metadata. Caller-selected native projections control their own returned fields.

## Method signatures

`Filter` below is `QueryFilter<T & { _id: string }>`, `Update` is Mongoose `UpdateQuery<T & { _id: string }>`, and `Write` is `{ context?: TransactionContext; session?: ClientSession; allowAll?: boolean }`. `Read` adds native `sort` and bounded `limit`. `View` adds native `projection: ProjectionType<T & { _id: string }>` and `populate: PopulateOptions | PopulateOptions[]`. `DistinctValue<V>` unwraps an array field to its native distinct element type. A full-record overload accepts `Read`; a projected/populated overload accepts `View` and returns `Partial<T>` for projection-only options, or an explicitly declared caller view `R extends object`. Population changes field types, so unspecified population views default to `Record<string, unknown>`; they never claim the original foreign-ID type. Optional view variables cannot select a false full-record overload.

The read, returned-update, returned-delete and pagination methods also have the `View` overload described above. Iteration has the same honest view overload. There are no `find`, `update`, `delete`, `scan` or count aliases. Summaries are plain objects reporting native counts; RepositoryBulkResult contains insertedCount, matchedCount, modifiedCount, deletedCount and upsertedCount. All bulk insertion IDs are caller-supplied. returned-record writes return the post-update record or pre-delete record, with `null` for absence. OrThrow methods use `RECORD_NOT_FOUND`.

## Bounds and transaction ownership

`findMany` defaults to 100 and accepts at most 1,000 records. Pagination defaults to page 1 and limit 20, accepts at most 100 rows per page and at most 1,000,000 skipped rows, and returns data, totalCount, totalPages, currentPage, hasNext and hasPrev. Results append unique indexed `_id` as the stable sort tie-breaker and use simple collation. Page and count run sequentially, preserving a caller's shared session. Without an explicit transaction they are separate reads, so concurrent writers can change the count between reads; callers needing a common snapshot supply their transaction.

Iteration uses a server cursor with bounded batch size (default 100, maximum 1,000) and result maximum (default 10,000, maximum 1,000,000, additionally capped by a supplied limit), stable `_id` tie-breaker and `finally` cursor cleanup on completion, early break or error. Native cursor advancement does not depend on projected fields; excluding `_id` cannot stop or duplicate traversal. Await iteration serially when sharing a transaction.

`MongoDatabase.run` creates a retryable native transaction and gives its participants one opaque context. Expired/foreign contexts are rejected. Repository options accept that context or a native session belonging to the selected connection. Supplying both is accepted only when they identify the same session; a mismatch fails. Population inherits the selected session recursively, rejects conflicting nested sessions, remains lean and forces ordered population queries inside transactions. A standalone server is refused: use a replica set or supported sharded topology. No fallback converts multi-record workflows into sequential nontransactional writes. External mail, password hashing, Firebase checks and realtime publication stay outside retryable callbacks.

The pinned MongoDB driver 7.8 uses a native 120-second retry-admission window per `withTransaction` call, with jitter/backoff for transient retries. The application additionally allows at most three duplicate-race calls and sets `maxCommitTimeMS: 10000` per commit action. In-flight callbacks/commands can outlive retry admission, and the driver can retry commit acknowledgements: neither 15 seconds nor a fixed total wall-clock bound is promised. Deprecated `timeoutMS` is deliberately absent because this driver treats it as a no-op. No Promise.race leaves database work running in the background.

Single-record operations outside a caller transaction use Mongo's native atomic operation; they do not open unnecessary transactions. `createMany` is different: it is atomic, limited to 1–1,000 entities, and saves sequentially in one transaction, running full schema validation and save middleware for every entity. Any failure rolls back all its writes. A supplied session must already have an active transaction; the caller owns commit/abort and must not catch an error and then commit a failed logical batch. `createMany` never runs parallel saves on one session.

Empty-filter writes require `{ allowAll: true }`, including bulk update/delete entries. Native updates require operators, reject replacement/pipeline forms and any direct ID mutation/rename, and enable Mongoose update validators. These validators apply to changed paths and supported operators, rather than validating a complete hydrated document; `$inc` and cross-field invariants still need deliberate owner operations. Unknown schema fields fail rather than being silently stripped into a whole-collection mutation.

`upsert` is an explicit string-ID operation. Its complete insertion candidate is schema-validated first; untouched insertion defaults are placed in `$setOnInsert` and fields addressed by other update operators (both the source and destination of `$rename`) are omitted from those defaults to avoid conflicting Mongo paths. Native update operators determine touched fields on insertion as well as update. The immutable ID is always set consistently. Native bulk upsert is refused in favor of this method; account/refresh/action security transitions continue to use their existing conditional owner methods and one shared transaction.

## Native bulk behavior

`bulkWrite` accepts 1–1,000 typed native operations, defaults to ordered execution and preserves native errors with their partial-result metadata. It maps insert IDs, all filters and keyed replacements consistently. Replacement requires the exact immutable ID in the filter; bulk update pipelines, ID changes and implicit bulk upserts are rejected. Mongoose casts the operations and validates inserts/replacements; per-operation skipValidation is forced false so it cannot weaken this guarantee. It does not run per-document save/update middleware or full document validation for update operations. Model bulk middleware may run according to the pinned Mongoose version.

Bulk writes are not automatically atomic. With ordered execution a server failure can leave earlier operations committed and prevents later operations; with unordered execution independent valid operations can commit while other operations fail. Unordered validation failures also throw after valid operations have been attempted (`throwOnValidationError: true`). A thrown result is not evidence of rollback. Supply an active transaction and let the error abort it when atomicity is required. No retry or error translation hides bulk partial outcomes. Aggregation returns plain explicitly typed pipeline records; Mongoose does not automatically cast aggregation stages.
