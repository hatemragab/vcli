# Identity and persistence reference

This is handwritten expected output for review before VCLI implementation. No CLI generation or phase acceptance is implied. `createIdentityRuntime(config, mail)` is exported from `src/modules/identity/identity.module.ts` and returns `{authority,module,close}` with idempotent resource cleanup. It opens the selected database and composes direct injectable services and explicit Nest modules. The obsolete store factories, composition wrappers and standalone runtime file are removed.

`AccountService`, `InstallationService` and `SessionService` inherit real shared CRUD from `src/core/database/base-repository.ts`; each owner keeps its types and Mongoose schema in its `.entity.ts` file. `AccountModule` registers and exports `AccountService`, and the account controller uses that service directly. `InstallationModule` and `SessionsModule` also export their deliberate services. Focused identity, password hashing, token verification, session issuance, refresh and management services own the remaining behavior. Identity orchestrates accounts, installations and sessions; those owners do not import identity. The neutral `EnrollmentCutoff` capability lives in `src/core/auth/enrollment-cutoff.ts`. Core imports no feature, and all runtime and type imports must form a DAG.

## Shared data-service contract

`BaseRepository<T extends {id:string}>` takes the selected `MongoDatabase`, model name, Mongoose schema and optional duplicate code. It exposes its protected native model to owner services and provides the [full native method catalog](base-repository.md), with honest projected/populated result types and explicit shared-session options. No runtime driver metadata or universal query abstraction remains.

The complete [native repository contract](base-repository.md) gives the current method signatures and failure semantics. Reads use `findById`, `findOne`, `findMany`, explicit absence variants and native filters; writes use named native update/delete operations and summaries. Full records, projections/population and aggregation records have different honest result types. `findWithPagination(pagination, filter, options)` is bounded and stable, and `{ context }` or a native session joins the caller's transaction. Page/count execute sequentially; no generic method is automatically exposed through HTTP.

MongoDB persists the same public `id` as its indexed string `_id`. By-ID operations and native logical filters map public ID predicates to `_id` while retaining ownership constraints. Sorting and distinct access on public ID use the same primary key. Default results retain public `id` and omit internal metadata; explicit native projections control their own selected fields. No duplicate ID index or automatic schema migration is needed.

`AccountService.lock` remains a database-specific authority lock. Active-session listing, revocation, one-use action and refresh consumption, credential-version replacement and rate spending remain specialized conditional/transactional operations. They are not replaced with unconditional generic CRUD. Schema creation and indexes are explicitly composed above core in `src/initialize-identity-database.ts`; changing a database recipe does not migrate existing data.

## Swagger request documentation

The selected identity routes expose required JSON request bodies in `/docs` even though their controllers accept `unknown`. Schemas use Zod 4 input-mode JSON Schema targeting OpenAPI 3.0, preserving strict object properties, required fields, optional platform defaults, capability patterns and revoke-scope variants. Zod remains the runtime authority for UTF-16 length and UTF-8 byte refinements; password field descriptions state those extra rules. Body examples contain only illustrative addresses/passwords, non-issued placeholder capabilities and an instruction to paste a real Firebase client ID token. Replace them before executing; no runtime credential is captured in the OpenAPI document.

Local password change and session operations document bearer authentication. Session revoke additionally exposes `X-Session-Token` as a conditional Firebase header: supply it with the Firebase ID token in that profile, and leave it unset for local JWT authentication. The revoke examples distinguish current, selected, others and all scopes, including their recent-authentication and ownership requirements. See [Zod input/output JSON Schema conversion](https://zod.dev/json-schema#input-output) for the selected conversion semantics.

## Endpoints

The root application adds `/api` to these routes. Bodies are strict Zod objects; unknown fields, including client ownership fields, are rejected. All returned timestamps are UTC epoch milliseconds. Responses carrying credentials use `Cache-Control: no-store`. Secrets belong in request bodies/headers over HTTPS, never URLs or logs. This is native bearer transport; there is no cookie/CSRF profile.

Only the selected profile's identity routes are registered. Local requests use `Authorization: Bearer <access JWT>`. Firebase requests use `Authorization: Bearer <client Firebase ID token>` **and** `X-Session-Token: <opaque app capability>`. A session UUID is never an external credential. Platform is bounded to `android`, `ios`, `web`, `other` and defaults to `other`.

Action mail carries a private link to `PUBLIC_ORIGIN/?action=<purpose>#token=<secret>`. A trusted client handler must read the fragment, promptly clear it from browser history, prompt the proof holder to choose a password, and POST `{token,password}` to the corresponding verification or reset confirmation endpoint. Verification must explicitly ask for the actual password; it must never silently submit an earlier registrant's stored choice. The backend never accepts a client continuation URL. A full client action UI is separate from these API handlers. Capture inspection is test-owned, with no public debug route. Mail rejection, unavailability or uncertain acceptance is deliberately absent from enumeration-sensitive public responses. A caller can request a new action after the rate window; dispatch does not blindly retry an uncertain SMTP submission.

Safe error codes include `INVALID_REQUEST`, `INVALID_CREDENTIALS`, `EMAIL_VERIFICATION_REQUIRED`, `INVALID_ACCESS_TOKEN`, `INVALID_REFRESH`, `REFRESH_REUSE`, `INVALID_ACTION`, `SESSION_REVOKED`, `SESSION_NOT_FOUND`, `RECENT_AUTH_REQUIRED`, `REAUTHENTICATION_REQUIRED`, `PROVIDER_DISALLOWED`, `FIREBASE_TOKEN_REVOKED`, `FIREBASE_USER_DISABLED`, `FIREBASE_UNAVAILABLE`, `RATE_LIMITED`, `HASH_CAPACITY`, `SESSION_LIMIT`, `DATABASE_UNAVAILABLE`, `DATABASE_BUSY`, and `COMMIT_OUTCOME_UNKNOWN`. Provider/driver exception text is not returned.

## Credential and revocation policy

Local identity keys are `local:<normalized email>`; trim/lowercase is the declared email policy, without provider-specific dot/alias folding. The identity primary key enforces canonical-email uniqueness in MongoDB. Firebase keys are `firebase:<project>:<verified UID>`; provider email is contact metadata and never an identity merge key. Phone-only accounts retain `email:null`. Account IDs, session IDs and installation IDs are independent cryptographic UUIDv4 values generated at the edge.

Passwords preserve supplied Unicode bytes, without normalization or truncation. Inputs require 12–128 UTF-16 code units and at most 256 UTF-8 bytes. Argon2id uses 19,456 KiB memory, two passes, one lane and a 32-byte result. Hash/verify concurrency is two per process with immediate capacity rejection; there is no unbounded queue. Boot measures the dummy-hash duration privately in `ArgonPasswords.measuredHashMs`. A focused Node 26.13.1 measurement on this VPS (16 November 2026) observed five serial hashes at 31/26/27/22/23 ms, two concurrent hashes in 26 ms total and process maximum RSS 112,996 KiB. This is a small local measurement, not a production performance certification. Stored self-describing hashes are checked for safe resource ceilings and rehashed after successful authentication if needed. Unknown-account login verifies the same dummy hash with the same public credential failure. Timing equality across networks is not promised.

Default lifetimes come from the shared config: access five minutes, session one day, recent authentication five minutes (maximum configured recent window 15 minutes). Verification actions last one day; reset actions 15 minutes. Verification confirmation, password reset and password change increment credential version, invalidate older verification/reset actions, revoke all sessions and require fresh login. Verification does not authenticate a session. Local access uses maintained `jose` HS256 with fixed trusted key ID `local-v1`, issuer, audience, required claims, expiry and current server session checks. Production requires `JWT_SECRET`; development can use a process-random ephemeral key, invalidating old access tokens on restart. Single-key rotation deliberately requires replacing the key and reauthenticating; overlapping signing keys are not implemented. Restrict access to this symmetric key and rotate/revoke on compromise.

Pending signup passwords cannot establish a verified credential. If an attacker signs up an email with password A and its owner later signs up with B, registration remains enumeration-safe and preserves the pending identity, but the email proof holder must explicitly choose the actual password at confirmation. That choice may be B or another valid password; it is hashed through the existing bounded Argon2 port before the retryable transaction. The same transaction consumes the purpose-bound unexpired proof, locks account authority, checks credential version, conditionally replaces the password with a version increment, verifies email and revokes obsolete session authority/advances its cutoff. Older actions and stale in-flight logins cannot later reestablish the superseded credential. A failed transaction rolls these writes back together; an uncertain commit acknowledgement still requires reconciliation. Already-verified accounts cannot accept verification confirmations or request fresh verification actions. Firebase-managed credentials and action emails retain their separate provider workflow.

This closes the pending-account pre-hijacking path; it does not establish a person's identity beyond possession of the emailed bearer capability. A stolen or forwarded valid proof authorizes its holder to choose a password. Protect the mailbox, delivery channel, trusted client and TLS; the API cannot infer who originally requested an email. The single-use/expiry and explicit new-password/session-invalidation mechanics follow the relevant [OWASP password recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html); using that mechanic for initial verification is this reference's explicit owner policy, not a claim that the guidance mandates this signup contract.

Refresh/action/session capabilities use 32 random bytes from Node cryptography. Only SHA-256 digests and necessary lifecycle metadata persist. Refresh consumes the current credential and inserts one random successor in the same transaction; consumed digests remain for replay detection. Session ID is also the family's scope: replay revokes only that family, preserving a separate login. Concurrent refresh may produce one successful response and then revoke that family's successor when the competing request is detected as replay. Clients must use one in-flight refresh per shared session. A lost response requires reauthentication; there is no retry grace or hash-only secret recovery. An unknown commit acknowledgement is reported as uncertain, never as rollback or permission to retry an ancestor refresh.

Accounts are the shared serialization boundary for issuance, revocation, password changes and enrollment cutoff. Each login/bootstrap creates its own installation record with generation one; no client-supplied installation ID, rebind, hardware attestation or cross-account installation transfer exists in this reference. Revocation removes session authority while preserving the installation record. Push consumers must use current principal authority; an installation ID alone grants nothing. Retention/deletion of historical records is an operator policy, not an implicit side effect of logout.

Rate buckets are durable in MongoDB and shared across limiter instances. Fixed one-minute windows permit login 20 per peer and six per canonical identity; refresh 60 per peer; other unprotected identity operations ten per peer and, where an identity is available, three per identity. Confirmation is peer-limited before hashing. Peer identity uses the actual socket remote address; deployments behind a proxy need an explicitly trusted ingress policy or intentionally share a bucket. Do not trust arbitrary forwarded headers. Database failure fails the check closed. Rate keys are hashes. Operators should periodically remove obsolete durable rate buckets; no background scheduler or unbounded cleanup transaction is started at boot.

The threat model includes stuffing/enumeration, stolen access/refresh/action secrets, replay/concurrent transitions, hash exhaustion, revoked Firebase reenrollment, key compromise and provider/database outages. TLS, reliable UTC clocks, protected process/storage/backup access and reviewed ingress rate limits are required assumptions. A compromised host/database writer is outside this reference's credential-isolation guarantee. Hash limits and request buckets bound application work but do not constitute network DDoS protection.

## Firebase profile and client setup

Use a real Firebase project with Admin Application Default Credentials supplied privately (for example `GOOGLE_APPLICATION_CREDENTIALS` pointing to a protected service-account file) and matching `FIREBASE_PROJECT_ID`. This reference refuses `FIREBASE_AUTH_EMULATOR_HOST`; no fake-token routes exist. Named SDK instances use fresh names and are deleted during runtime cleanup. Auth and push may use independent SDK instances without interfering with each other's lifecycle.

`verifyIdToken(token,true)` checks signature, project/issuer, audience, expiration and current disabled/revoked-user state. Disabled, revoked, invalid and unavailable outcomes remain distinct. No successful authority cache exists. `current(sessionId)` also performs a provider user-status/revocation check outside the database transaction, then rereads application authority. Existing realtime consumers can therefore fail closed on provider outage/revocation instead of relying solely on the local record. There remains the normal in-flight observation gap after verification and before an external disclosure; transports define their own recheck/disclosure bounds.

All four sign-in methods (`password`, `phone`, `google.com`, `apple.com`) are enabled by the application's default allowlist. The allowlist is checked at enrollment and on every authorization, including existing sessions. Changing an in-memory config requires restarting/replacing all instances. Merely disabling a console sign-in method does not invalidate already-issued ID tokens; update the application allowlist and/or revoke provider authority. Local session revocation does not call Firebase's account-wide `revokeRefreshTokens`, which would destroy intended sibling sessions. There is consequently no external provider-revocation job to fabricate as completed.

Clients perform real sign-in/refresh using Firebase client SDKs. Obtain the ID token, POST bootstrap, store the opaque app capability in a platform-protected secret store, and pair it with current client ID tokens. Refreshing the Firebase ID token preserves the same application session. Bootstrap is a deliberate new app-session enrollment, not a retry protocol that recovers lost server-generated capabilities; a lost bootstrap response may leave an inaccessible session until expiry. Use an existing authorized capability after token refresh. A fresh bootstrap needs recent `auth_time` (not token `iat`) and strictly greater auth time than the durable account cutoff. Every scoped application revocation advances that cutoff under the same authority lock while leaving authorized sibling records intact. Firebase times have one-second granularity: reauthenticate in a later second than the cutoff. A fresh ID token from the old authentication is insufficient. For sensitive non-current revocation with an old app session, perform recent provider authentication and enroll a new app session; its authentication fact supplies the recent-session requirement.

Required external setup, separately unverified:

- Email/password: enable Email/Password in Authentication and configure authorized client domains; use client registration/sign-in and Firebase's own action-email support or a separately configured Admin action-link workflow. Backend local-password endpoints do not appear in Firebase mode.
- Phone: enable Phone and authorized domains, configure the client platform's app verification/reCAPTCHA and actual SMS policy/billing. A verified provider phone remains provider identity, without an invented contact email.
- Google: enable Google, configure OAuth consent/authorized domains and each client's platform identifiers/signing fingerprints/redirects. Sign in through the client SDK, then send its Firebase ID token, never a raw Google token as an API credential.
- Apple: configure Apple Developer identifiers, private key/team/key references in Firebase, return URL/domain and each native capability. Review private-relay email sender setup when sending to relay addresses. Complete real Apple client sign-in; never infer success from backend compilation.

Link/unlink, account deletion and cross-provider migration are not exposed. Email text cannot authorize linking. Firebase-managed verification/reset are client/provider workflows, separate from the local action-token endpoints and SMTP application mail. Implementing the Admin-generated, application-delivered Firebase email option remains a delivery extension; it is not claimed here.

Official references checked 16 November 2026: [Admin token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens), [Admin session management](https://firebase.google.com/docs/auth/admin/manage-sessions), [Admin Node source for revoked/disabled checks](https://github.com/firebase/firebase-admin-node/blob/main/src/auth/base-auth.ts), [password client sign-in](https://firebase.google.com/docs/auth/web/password-auth), [phone sign-in](https://firebase.google.com/docs/auth/web/phone-auth), [Google sign-in](https://firebase.google.com/docs/auth/web/google-signin), [Apple sign-in](https://firebase.google.com/docs/auth/web/apple), and [Admin email action links](https://firebase.google.com/docs/auth/admin/email-action-links).

## Persistence and release initialization

This app contains only MongoDB/Mongoose. `DATABASE_URL` must identify a replica set or supported sharded transaction topology; a standalone server is refused. `DATABASE_DRIVER` is rejected rather than implying switching is supported. Production requires its explicit private URL. String `_id` stores the public ID/key/digest consistently; owner services retain conditional updates, credential versions, strict refresh and authority locks.

`MongoDatabase.run` issues one opaque context tied to its native connection/session. Participants reject expired/foreign contexts and execute sequential operations on that shared session. The pinned MongoDB 7.8 driver admits transient retries within its native 120-second window per withTransaction call; explicit duplicate races permit at most three such calls. maxCommitTimeMS is 10 seconds per commit action, not a total wall-clock deadline. Deprecated/no-op timeoutMS is absent; in-flight work can outlive the retry window. Crypto, Firebase verification and mail submission remain outside retryable callbacks. Database errors preserve safe application failures and `COMMIT_OUTCOME_UNKNOWN`; raw provider messages remain private.

Ordinary identity/notes startup checks prepared schemas rather than silently migrating. After building current source, run `DATABASE_URL=<prepared-local-url> node scripts/migrate.ts`. This initializes all four schema owners: identity, notes, media and push. Identity creates its explicit owner collections/indexes under a unique migration lock and marks completion last; successful repeated setup is preserving. A failed incomplete identity migration retains its lock for deliberate operator reconciliation. Notes preserves older string-`_id` records by backfilling public `id` during explicit setup. There are no SQL migrations or runtime database profiles in this application.

## Evidence and remaining acceptance

The identity policy suite preserves email-proof credential establishment, version advancement/session revocation, strict refresh reuse, account/installation ownership, Firebase enrollment/revocation policy, recent authentication, durable rate limits, rollback and concurrency coverage. Provider/password fakes prove policy separately from real local database behavior; Argon2/JOSE and SDK error mechanics retain their focused checks.

The [native BaseRepository contract](base-repository.md) defines every method, projection/population shape, bounds, session ownership and createMany/bulk failure semantics. Its tests cover primary-key query/explain evidence, plain object isolation, invalid/foreign contexts, whole-collection opt-in, native operations, projected cursor traversal, transaction rollback and partial bulk outcomes.

Use one isolated `TEST_DATABASE_URL` after applying all owner schemas. Missing infrastructure produces explicit setup skips; tests never select a memory application database, start services or migrate a production database. For example, after building current source:

```sh
TEST_DATABASE_URL=<prepared-local-url> node --test --test-concurrency=1 test/base-repository*.test.ts test/identity*.test.ts
```
