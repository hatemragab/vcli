# Private media in the reference application

This is hand-built expected NestJS output for review. It does not implement VCLI or complete its storage phase. Private local storage and the PostgreSQL state store are implemented; external AWS/R2 conformance remains pending. `S3_PROFILE=custom`, direct presigned transfers and multipart transfers are explicitly unsupported and rejected. No placeholder grants are returned.

## Compact module composition

`media/media.module.ts` exports `createCapabilitiesRuntime` and `initializeCapabilitySchemas`; obsolete runtime factory and compatibility exports are removed. The runtime still returns `{ module, close }`. Its capability composition imports independent `MediaModule`, `PushModule` and `MailModule`; the media feature itself consumes storage and shared HTTP security. `MediaService` is directly injectable from `media/media.service.ts`, and `StorageService` is directly injectable from `storage/storage.service.ts` through `StorageModule`.

The flat storage folder owns local staging/finalization, private filesystem mechanics and S3 implementation. Storage accepts a narrow immutable `StorageObject` shape from `storage/storage.entity.ts`; it never imports media or push, including through types. `StorageService` routes saved object profiles, while local and S3 implementations handle their concrete I/O. Its cache contains SDK clients keyed by the persisted immutable profile, not application service lookups. Changing the configured default preserves historical routing. Nest constructs services through ordinary providers; no global module, locator or circular import is used.

`MediaRepository` is an internal specialized helper for quota reservations and conditional lifecycle transitions. Its PostgreSQL state store preserves aggregate atomicity; generic shared CRUD does not replace those transitions or expose unrestricted mutations. Source/entity, storage and HTTP projections remain separate, and only `MediaService` is exported as the media business capability.

## HTTP contract

Root composition supplies `/api`. Every media route uses the shared principal guard and current application-session authority. Firebase requests need the ID token and application session secret; local requests need the access JWT. No caller can supply an owner, provider key or filesystem path.

| Endpoint                               | Input and result                                                                                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/media/uploads`              | Strict JSON `{filename, bytes, sha256, mode?: 'mediated'}`; SHA-256 is lowercase full-object hexadecimal. Returns a reserved attempt/media ID and authenticated transfer path. |
| `PUT /api/media/uploads/:id/content`   | Raw `application/octet-stream`, streamed to the private staging file; returns uploaded metadata after exact size/hash validation.                                              |
| `POST /api/media/uploads/:id/finalize` | Validates/promotes exact bytes and returns ready metadata; retry reconciles an existing committed object.                                                                      |
| `GET /api/media`                       | Safe metadata for this account's attempts and media; no root, bucket, token or object key.                                                                                     |
| `GET /api/media/:id/content`           | Account-authorized ready object, attachment, octet-stream, `nosniff`, CSP sandbox, private/no-store.                                                                           |
| `DELETE /api/media/:id`                | Marks deletion durably, deletes the exact owned provider object/staging file, then releases the reservation. Retry resumes deletion.                                           |
| `POST /api/media/cleanup`              | Bounded cleanup of this account's expired attempts; returns removed/pending counts. Also runs before beginning another upload.                                                 |

The same account's active sessions can access its media. A different account gets `MEDIA_NOT_FOUND`; this does not reveal whether an ID exists elsewhere. There is no public static directory or unauthenticated upload/download grant. A streaming request checks authority at request start; revocation during its bounded lifetime does not recall bytes already transferred. OpenAPI includes explicit begin/body schemas, UUID parameters, Firebase session-header guidance and a raw octet-stream binary body for Swagger try-it-out.

Default maximum object size is 5 MiB (`UPLOAD_MAX_BYTES`, up to 100 MiB). The reference's fixed per-account policy is four outstanding attempts, 128 retained entries and 256 MiB reserved plus committed bytes. Filesystem transfer/download deadlines are 30 seconds; each HTTP instance allows four uploads, four finalizers and four downloads. Transfer checks byte count while writing and computes full SHA-256 and MD5 with bounded buffers; neither filename nor client MIME metadata proves content format or malware safety. Untrusted HTML/SVG is downloaded as an attachment. There is no inline rendering, format scanner or malware scanning claim.

## Persistence and lifecycle

The media owner persists its bounded per-account aggregate in the PostgreSQL `reference_media_owners` table. It stores revisions, attempts, reservation amounts, evidence and immutable final object references. Initial row creation and guarded updates share a Drizzle/pg transaction with `FOR UPDATE`. Quota reservation and lifecycle transitions remain atomic owner operations. SDK/file I/O never runs inside those callbacks; there is no application memory storage recipe.

States are `reserved → receiving → uploaded → finalizing → ready → deleting`; failed transfers remain `failed` until safe cleanup. Reservation release is idempotent and follows confirmed cleanup. Expired receiving state waits beyond grant expiry plus the transfer deadline before removal. Failed/expired attempts are not silently counted as freed while bytes could still be written. Ready media is not automatically expired.

Final records retain the complete immutable storage-profile reference: local canonical root, or the versioned AWS/R2 bucket, region, endpoint and addressing selection. Each record also retains its staging root. Changing the configured default does not reinterpret existing objects or move data. Old profiles still need their paths and credentials available; removing those resources makes their operations unavailable rather than redirecting them to the new default. No migration engine is provided.

Only the request that atomically changes `uploaded` to `finalizing` may create an object. Later requests only reconcile the exact object and full SHA-256. Thus a delayed finalizer cannot write after a reconciler makes the object ready and a subsequent delete removes it. A lost provider acknowledgement or database write leaves durable `finalizing`, with quota retained, and returns completion unknown. If the provider object exists with the expected full hash, retry can recover it. If the process died before creating bytes, absence cannot establish that an earlier request will never finish: this conservative reference retains unknown state for operator review. An automatic lease/abandonment protocol for that case is unfinished; neither cleanup nor a retry blindly frees it or issues another write.

Missing media, expired upload, size/integrity errors, quota/state conflicts, unavailable providers and unknown completion have separate safe codes. Unknown/deleting state is visible in the account's metadata list. No full path, raw provider exception or signed credential is returned.

## Local setup

Set `STORAGE_DRIVER=local` and `LOCAL_STORAGE_ROOT` to a persistent, application-owned private directory outside anything served by a reverse proxy. The root and its incoming/object directories must have mode `0700` and belong to the service user. Existing non-private roots are rejected, never silently chmodded. Every ancestor must be an ordinary directory; configured or replaced symlink ancestors, traversal and symlink files are refused. IDs and path segments are generated by the server. Uploads use `O_CREAT|O_EXCL|O_NOFOLLOW`; reads use `O_NOFOLLOW` and inspect the opened file. Finalization removes write permissions and uses an exclusive hard link, never rename-overwrite. The root is assumed inaccessible to unrelated writers; a privileged process or another process running as the storage owner is outside this isolation boundary. The filesystem must support these POSIX operations.

Use a declared single-instance persistent volume and back up media together with database references. Process restart is supported by persistent metadata/files. Per-container local disks do not provide shared storage across replicas. Multiple API instances also need shared private staging for in-progress mediated S3 transfers. Neither the application nor this document provisions volumes, schedules backups or certifies a multi-replica topology.

## S3 setup and explicit profile limits

All selected S3 uploads remain mediated through private local staging. The server then submits one conditional `PutObject` with `If-None-Match: *`, exact `ContentLength`, `Content-MD5`, attachment/octet-stream metadata and no ACL. It verifies the resulting object by streaming a complete `GetObject` and comparing byte count plus SHA-256, including after an uncertain PUT. ETag and HEAD are not treated as content hashes. AWS additionally receives the explicit full-object SHA-256 checksum; R2 uses its documented MD5 operation plus full-object readback and does not inherit unsupported AWS checksum/encryption headers.

| Profile                    | Required settings and assumptions                                                                                                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AWS                        | `STORAGE_DRIVER=s3`, `S3_PROFILE=aws`, private `S3_BUCKET`, actual `S3_REGION`; no endpoint override. `S3_FORCE_PATH_STYLE` explicitly selects addressing. Standard AWS credential chain supplies scoped credentials.                             |
| Cloudflare R2              | `S3_PROFILE=r2`, private bucket, `S3_REGION=auto`, HTTPS account endpoint ending in `.r2.cloudflarestorage.com`, explicit addressing. Standard AWS credential-chain variables can carry the R2 API credentials through private runtime injection. |
| Custom compatible endpoint | Configuration is recognized but rejected with `UNSUPPORTED_STORAGE_PROFILE`; add a reviewed profile and real conformance evidence before enabling it. An arbitrary endpoint is not certified by AWS/R2 tests.                                     |

The pinned `@aws-sdk/client-s3` performs SigV4 signing and HTTP mechanics. Request/response automatic checksum behavior is explicitly `WHEN_REQUIRED`; no provider-specific CRC/trailer defaults are silently sent to R2. SDK retry is one attempt; PUT uncertainty is resolved by readback, never an unconditional overwrite. SDK connections are bounded and operations abort after 20 seconds. Credentials are not stored in object metadata or persisted profiles.

Use a dedicated private prefix/bucket and least-privilege Get/Put/Delete permissions. Every application write path is conditional; clients never receive write credentials. On AWS, enforce conditional writes in bucket/IAM policy as appropriate. Do not allow another application writer to overwrite these keys. Administrative/provider mutations are outside the immutable application-object contract. Bucket encryption/retention, public-access blocking and access auditing require operator setup. R2 does not receive AWS ACL/KMS fields by default. Lifecycle rules must preserve committed objects and must not expire the whole owned prefix; this profile has no multipart uploads to abort.

Browser-to-bucket CORS is unnecessary for this mediated mode. Configure the API's explicit allowed origins, normal authenticated requests and `application/octet-stream` transfer. Do not provision permissive bucket CORS to imply presigned support. Future presigned/multipart work must bind size/integrity/conditions into grants, verify final immutability, validate manifests and prove exact provider/browser CORS behavior before being enabled. Download stays mediated so there is no independently valid signed URL after logout.

## Schema setup and evidence

Development/test startup initializes only these owner schemas. Production startup checks for existing schemas and does not create/migrate them. A separately authorized setup step calls `initializeCapabilitySchemas(config)` from `dist/modules/media/media.module.js`; this also initializes the push owner's schema through its public boundary. It creates only the reference owner tables/collections and does not alter existing production schemas. Review database permissions and backup policy before using it.

Focused checks are `node --test --test-concurrency=1 test/media.test.ts test/media-persistence.test.ts` after a fresh build, with a dedicated `TEST_DATABASE_URL`. Fixtures initialize all four owners in isolated schemas; absent infrastructure is an explicit skip. Cases cover atomic quota races, ownership, conditional transitions, reconnect persistence, streaming/size/hash failures, cancellation, path/symlink denial, immutable replay, deletion and reconciliation. S3/provider command-shape fakes prove translation only. The [current verification record](VERIFICATION.md) identifies native PostgreSQL/runtime acceptance separately from external AWS/R2, browser-to-bucket, scanning, deployment and backup acceptance.

Primary references checked 16 November 2026: [AWS SDK v3](https://github.com/aws/aws-sdk-js-v3), [AWS conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/), [Node filesystem](https://nodejs.org/api/fs.html). Hosted AWS/R2 acceptance, custom endpoints, direct grants, multipart and automatic recovery of absent unknown completions remain visible gaps.
