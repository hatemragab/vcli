# Operations and diagnostics reference

These are hand-built review artifacts for expected future VCLI output. Actual local application, database, protocol and browser evidence is recorded in the [current verification record](VERIFICATION.md). These artifacts do not establish generator phase completion, an executed Compose topology, image build/run, automated deployment, provisioning, backup/restore or isolated-production diagnostics acceptance. Use standard Nest/package scripts for development and the compiled `node dist/main.js` process in production, with platform-native lifecycle and signals.

## Local selected services

[Compose](../ops/compose.development.yml) supplies optional `postgres`, `centrifugo` and `diagnostics` profiles. This application always uses PostgreSQL/Drizzle + pg. `DATABASE_URL` is required; `DATABASE_DRIVER` is rejected. The app remains a native Nest watch process.

The PostgreSQL 16.16 image is pinned by version and digest. Native application/database acceptance is recorded in [verification](VERIFICATION.md); Compose topology and image build/run acceptance remain pending. Combined-app verification is historical. Example operator command (not executed by this worker), from this PostgreSQL app:

```sh
docker compose --env-file <private-services-file> -f ops/compose.development.yml --profile postgres up -d postgres
```

PostgreSQL is loopback port 55432 with user/database `reference`; fill the password privately and set the matching private `DATABASE_URL`. The image persists at `/var/lib/postgresql/data`. Build, then `make migrate` initializes all four owners (identity, media, push and notes); run before normal startup and repeat safely. The demo uses that initialized dedicated local DB and private mail capture, refuses production, and reuses a valid disposable fixture credential on restart. It never resets unrelated data.

Named data volumes survive ordinary stop/redeploy. `down` preserves named volumes; `down -v`, prune/reset and replacing volume identities are destructive actions outside routine operation. The examples set explicit memory/CPU/PID budgets (512 MiB per database, 192 MiB Centrifugo, 128 MiB Vector) rather than claiming measured capacity. Check aggregate resources/download batch size first: service startup can pull missing images. Reuse cached compatible images where approved; verify any changed version's contracts.

Contributor-specific cgroups belong in [the local override](../ops/local/compose.orca.example.yml), not generated application policy. On this Orca VPS the operator must include a private local override setting `cgroup_parent: orca.slice` for each selected extra container and keep the shared resource budget. The application artifacts never change host limits. The generic Makefile uses this Compose path; enable the chosen profile explicitly, for example through `COMPOSE_PROFILES=postgres`. The default with no profile intentionally starts no infrastructure.

Centrifugo setup is in [realtime](realtime.md). Its public client port is loopback 58000, separate internal API/health port 59000, with host-gateway callbacks configured for a native app. Set both independent private credentials and callback header JSON in a private services file before selecting that profile. `GET http://127.0.0.1:59000/health` is service health only; it does not establish grant/proxy/publication behavior. In a containerized app topology change callback endpoints to the correct private API hostname and restrict ingress.

## Retained events and read-only MCP

The application composition opens the bounded [DiagnosticsService](../src/modules/diagnostics/diagnostics.service.ts) retained writer in `EVIDENCE_DIRECTORY` (default `var/evidence`) before database/provider initialization. It owns that writer's lifetime independently of realtime. The shared [AppLoggerService](../src/core/logging/app-logger.service.ts) is the application's emission entry point: bootstrap, Nest, HTTP and realtime use the same allowlisted event contract. Pino writes structured JSON to stdout and the logger forwards the same sanitized event facts to the bounded writer. Each output can fail independently without throwing into business work. The default asynchronous Pino stdout destination has a 256 KiB buffer ceiling; `logger.status()` exposes malformed-input, stdout-failure/drop and sink-failure counters. Shutdown gives stdout flushing a bounded deadline separately from retained-writer flushing; neither proves delivery to an external collector. Configuration failures before a safe diagnostics configuration exists are stdout-only; no environment file, raw configuration or provider error is logged.

`LoggingModule.register(logger)` explicitly exports `AppLoggerService` and the small `DIAGNOSTIC_EVENTS` capability as aliases of that logger instance. Consumers import the module through their normal composition; there is no global module or service locator. [DiagnosticsModule](../src/modules/diagnostics/diagnostics.module.ts) exports the retained writer, `DiagnosticReaderService` and `DiagnosticsMcpService`. Those storage/query services remain independent of realtime and application bootstrap. The event schema lives in `core/logging`; the consumer-facing capability remains in `core/diagnostics`.

The logger accepts fixed event names, severity, validated UUID request/operation/run identifiers, stable allowlisted error codes, canonical route templates, HTTP method/status and bounded numeric facts. Pino adds fixed project/service/environment, UTC timestamp and schema version. The retained writer adds its own writer/sequence identity. Unknown fields are discarded before either destination: messages, error objects/stacks, headers, cookies, bodies, action links, tokens, raw URLs, provider responses and raw environments are excluded. Nest framework calls become a fixed `framework.log` event and severity; their arbitrary message, stack and context arguments are deliberately omitted. Use structured allowlisted events for application diagnostics rather than relying on free-form framework text.

The logger uses per-instance `AsyncLocalStorage` to propagate approved correlation fields across asynchronous work. HTTP middleware accepts only a valid UUID request ID, otherwise generates one, and sets response correlation headers. HTTP terminal observations include method/status, duration and a recognized route template; safe exception observations include a stable code. Mutation-operation terminal events describe the HTTP operation outcome, not external delivery, persisted state outside that operation or a test assertion. A connection that closes before `finish` produces one terminal observation with synthetic status 499 and `REQUEST_ABORTED`; 499 is diagnostic metadata, not an HTTP status sent to the client, and an interrupted response does not establish whether business work committed. Job/provider/database boundaries require their own deliberate context propagation and instrumentation before they are advertised as covered.

The reader revalidates/strips each retained record. Do not put a credential in an identifier or error code. Malformed/invalid records are discarded with explicit gap metadata, never returned verbatim. The writer uses mode 0700 directories, 0600 exclusive/no-follow files and a single-writer lock. A same-user process can still change those files; these permissions are not a sandbox.

The writer queues at most 128 records, each at most 2 KiB, rotates before configured file size, and retains at most the configured file count. Defaults are three 1 MiB files; this is a byte/count policy with **no promised time horizon**. Only its exact `events-<timestamp>-<uuid>.jsonl` namespace is removed by retention. Caller operations do not await filesystem/collector/viewer I/O. Full queues, unavailable storage, another writer or filesystem failure drop diagnostic events, never retry business operations. `DiagnosticsService.status()` on the explicitly injected writer reports availability, drops, malformed input and queued count. On close the flush deadline is one second; lack of flush is incomplete evidence, not business failure or successful collection. Do not share this writer directory between app instances.

After an abnormal process exit, `writer.lock` may remain. Establish that no writer owns the exact directory before removing that one lock manually; do not delete evidence or another process's lock blindly. Diagnostics failure leaves the application operating with unavailable evidence. An infrastructure outage cannot cause unbounded application logging buffers.

Build through the normal app tooling, then launch the offline MCP facade in an explicitly configured environment:

```sh
env -i PATH="$PATH" NODE_ENV=development EVIDENCE_DIRECTORY=var/evidence node scripts/diagnostics-mcp.mjs
```

Set EVIDENCE_MAX_BYTES/EVIDENCE_MAX_FILES in that explicit environment too if the writer uses nondefault limits. The launcher constructs `DiagnosticReaderService` and `DiagnosticsMcpService` from the compiled `.service.js` files; it imports no application/provider bootstrap, dotenv, shell, Docker or deployment tools. `DiagnosticsMcpService` configures the pinned MCP SDK server directly, with its real stdio transport and only protocol traffic on stdout. Restrict inherited environment and OS permissions in the MCP client's process definition. The environment directory is an operator-controlled startup setting; tool input cannot supply arbitrary paths. **A separate same-user process is not an isolation boundary.** Remote transport, read credentials, egress restrictions and stronger isolated/production profiles are unsupported/pending, rather than implicitly inherited from app credentials.

Delivered tools are `project.describe`, `capabilities.list`, `diagnostics.status`, `logs.search` and `operations.timeline`, all declared read-only. There is no `tests.getResult` because test-result collection is not implemented; no tool runs tests, SQL, shell, Docker, generation, deploys, reads arbitrary files or mutates app state. Evidence text remains untrusted data even when a caller interprets it with an agent. The local OS user is authorized to the fixed `reference-api`/selected-environment scope and its retained runs; there is no unauthenticated remote endpoint or caller-selected project/environment.

Search accepts only structured `since`, `until`, `event`, `severity`, UUID `requestId`/`operationId`/`runId`, result `limit` (1–100) and its own cursor. If both time bounds are supplied, the range is at most 24 hours. Searches and status snapshots share a limit of two concurrent reader operations, with no reader queue; saturation returns `DIAGNOSTICS_BUSY`, and completion or failure releases the slot. At most 2 MiB is scanned per search call; pages can be truncated even with zero matches. Cursors are HMAC authenticated, bound to exact scope/filter/result limit and retained file identity/size snapshots, valid five minutes in the same reader process. They expire explicitly after retention/rotation removes a referenced file, scope/filter mismatch, modification/truncation, tampering or process restart. New data appended after a snapshot requires a fresh query, not an assertion that it did not happen. Files are bounded and no-follow/regular-file checked before reading. Queries expose no raw filesystem paths.

Pages report events, next cursor, truncation, scanned bytes, latest matched event age, unknown ingestion delay, unavailable sources and gap/retention limits. Actual coverage is sanitized **application** events only. Database statements, worker/infrastructure events, Vector/viewer observations and exact overflow/crash-loss counts are unavailable to this offline reader and reported as such. Writer sequence is local-process metadata, not cross-service causality. Missing events and nearby timestamps prove neither operation outcome nor absence; retain actual assertions separately. HTTP correlation is propagated within the application logger. Jobs, separate workers, database observations and provider callbacks still need deliberate correlation and source instrumentation when added.

## Vector and Logdy live feed

[Vector config](../ops/diagnostics/vector.yaml) reads only this application's already sanitized rotated JSONL, checkpoints to its private named volume, validates the fixed schema/project/service scope, parses into a fresh allowlisted object and drops malformed/unknown events. It preserves approved request/operation/run IDs, writer/sequence identity, route, method/status, duration, count and safe error code; it never forwards the original message or extra fields. It does not mount a Docker socket or collect arbitrary container/database stdout. Its live sink uses documented newline-delimited TCP JSON with a 128-event memory buffer and `drop_newest` when full. A disconnected viewer can lose live events; the application continues, and bounded local JSONL remains the historical source. This file is not a general infrastructure-log sanitizer; adding a source needs its own parse/redaction/coverage acceptance. Vector process/container logs need their separate bounded retention too.

The real supported Logdy mechanism here is **`logdy socket`**, not an invented HTTP ingestion API. [The live-feed launcher](../ops/diagnostics/logdy-live.sh) targets reviewed Logdy v0.17.1, binds its UI to `127.0.0.1:58080`, disables update checks/analytics and limits its FIFO to 1000 messages. A consuming operator installs/reviews that binary separately. Vector's Docker sink reaches `host.docker.internal:58233`; configure `LOGDY_FEED_IP` to the actual private Docker host-gateway interface, with the host firewall admitting only this project's Vector network to 58233. A host listener bound only to 127.0.0.1 is not reachable from a bridge container; this explicit setup is required before using the Compose feed. Never bind the unauthenticated feed/UI to public interfaces. When using native Vector instead, configure its sink and Logdy feed to loopback together.

The topology is `AppLoggerService -> bounded rotated JSONL -> Vector -> Logdy`, with stdout as a separate operator output and `DiagnosticReaderService`/MCP reading the same retained JSONL directly. Retention and offline queries therefore continue when Vector or Logdy is stopped. Infrastructure sources are not present in this profile; adding one requires an explicit parse/redaction transform, independent retention and source-coverage acceptance before its data reaches a viewer or reader.

The config contains 17 Vector transform unit tests for approved field preservation, private sentinel removal, malformed/foreign records, unknown events and invalid bounded fields. All 17 passed using the actual Vector 0.62.0 binary in each independent example; the final transform compiles without the unused-expression warning. Expected mapping/drop messages from malformed-input cases are rejection evidence, not failed tests. With the reviewed Vector binary already available, run `vector test ops/diagnostics/vector.yaml` from the app root. This command exercises Vector/VRL itself without starting the file source or network sink; YAML parsing alone does not validate VRL. Transform tests do not establish live collection, socket delivery, permission enforcement, rotation or outage behavior.

Start Logdy through its launcher and start only the diagnostics Compose profile after verifying the network scope, source permissions and binary/image versions. Actual Vector/Logdy service execution remains separate from source/static/transform checks; see [verification](VERIFICATION.md) for recorded results. Test normalization/redaction with isolated sentinels, viewer disconnection/overload, rotation and exact source coverage before treating the live view as operational evidence. The Logdy FIFO is a live viewer, not historical storage, an authorization service or a test assertion. Restrict its OS user; a read-only filesystem mount or endpoint flags cannot establish cross-project isolation. The native loopback feed and retained-reader availability after viewer termination passed in this update; [the verification record](VERIFICATION.md) describes the exact commands. Docker/host-gateway networking, browser rendering, reconnect, sustained overload, stronger isolation/access-negative tests and remote backends remain pending.

The opt-in native backend feed check is `VECTOR_BINARY=/absolute/path/to/vector LOGDY_BINARY=/absolute/path/to/logdy node --test --test-concurrency=1 test/diagnostics-live.test.ts`. Use reviewed Vector 0.62.0 and Logdy 0.17.1 binaries. The test copies the checked-in config, changes only source/checkpoint paths and the live address to task-owned temporary storage and loopback ports, limits Vector to one processing thread, and terminates its own processes. It verifies received JSON and continued retained logging after the viewer stops; it does not inspect the web UI or certify the Compose network. Without both explicit binary paths this optional test reports its setup requirement and skips.

## Image, deployment and release

[Dockerfile](../ops/Dockerfile) builds pinned ordinary Nest source in one stage and installs production-only dependencies into a non-root compiled Node image. Use `docker build -f ops/Dockerfile .` from the app root only when authorized. [Its specific ignore file](../ops/Dockerfile.dockerignore) allowlists source/build metadata/scripts/migrations and excludes private environment/key files; [ops/.dockerignore](../ops/.dockerignore) is the companion conventional artifact. No private settings belong in build args/layers. Inspect the context and resulting image before publishing. Current image evidence is structural only; image build/run acceptance remains pending in the [verification record](VERIFICATION.md).

The image creates `/app/var`, `/app/var/storage` and `/app/var/evidence` with mode 0700 and `node:node` ownership (UID/GID 1000). Mounted volumes replace the image directories: the operator must prepare and verify each mounted root with mode 0700 and UID/GID 1000 before starting the API, preserving existing contents. The storage adapter rejects group/other permission bits or a different root owner. Image permissions do not repair an existing volume; there is no privileged runtime permission initializer or automatic volume ownership change.

The runtime executes one compiled Node process. Docker/platform signal forwarding, restart/stop and health lifecycle own it; no custom supervisor or CLI runtime is needed. Example production memory/CPU/PID bounds and a 15-second termination grace are explicit artifacts, not performance evidence. Readiness establishes only the implemented dependency contract. Run one API replica: local uploads, local diagnostics, local tickets and in-process fanout have no tested shared-instance contract. Selecting S3 alone does not make sessions/fanout/tickets clustered.

These are artifact/manual-operator routes. There is no authenticated Dokploy/Coolify/CapRover apply/discovery/reconciliation operator implementation. Creating accounts, DNS, registries, secrets, volumes, databases, buckets or paid resources requires separate authorized operator actions. Target versions, resource IDs, image digests, routing/state/recovery tests and live evidence are pending independently for each platform. Private database/provider/diagnostic APIs remain private; do not expose Centrifugo internal port/API or backend proxy routes at public ingress. Coolify's provided artifact explicitly selects Socket.IO/local storage; edit and review the actual conditional configuration and service plan before selecting alternatives.

The complete release setup entry point is `node scripts/migrate.ts` **after `npm run build`**, run from the application root (`/app` in the image) with the same private runtime configuration as the replacement API. [The delivered script](../scripts/migrate.ts) loads `APP_ENV_FILE` only when explicitly configured and initializes identity, media, push and notes in sequence. All four owner schemas are required on a fresh production database, even when outbound push is disabled. The narrower `node migrations/initialize-identity.mjs` command initializes only identity state; it does not prepare media, push or notes and cannot replace the complete release action.

Identity initialization uses transactional advisory locking and `ref_migrations`. Media and push each create their owner table under a transaction-scoped advisory lock. Notes creates its table and index under its own advisory-locked transaction. Repeated compatible setup preserves data; these actions do not validate or upgrade arbitrary preexisting structures, transform old data, provide versioned media/push/notes migration history or atomically release all four owners. Incompatible structures require operator review. `make migrate` is an explicit bounded setup sequence, separate from ordinary startup, which only checks initialized schemas.

No ordinary app boot runs release migrations independently. For each release, record image/schema/current resource identities, quiesce conflicting release work, execute the complete command as one identified native release job, inspect the identity history/marker and all four owners' resulting structures, and only then replace the API. A later owner can fail after an earlier owner completed. Failure or lost acknowledgement stops the release until the actual database state is inspected/reconciled; retry only after confirming compatible state and resolving incomplete initialization. A generic retry is not an exactly-once guarantee. Future schema changes need reviewed versioned migrations and expand/contract compatibility. An old image cannot roll back a changed database automatically.

## Backup and restore procedure

This is a concrete operator runbook using native tools; **no backup or restore was performed**. Select a private encrypted backup destination, retention schedule and owner outside the app image. Protect database dumps, upload data, credentials and restricted action payloads separately from sanitized diagnostics. Platform configuration backups alone do not establish coverage of app state.

1. Record exact database/volume/bucket identities and release/schema version. Stop API writers (and any future real workers) through native lifecycle so database metadata and local upload bytes form a consistent application snapshot. No worker/scheduler currently exists to claim coordinated ownership. Preserve existing services/volumes; do not reset them.
2. PostgreSQL: use matching native `pg_dump --format=custom --no-owner --file=<private-backup-file> <private-connection-reference>` via an approved private credential mechanism (prefer `PGSERVICE`/protected `.pgpass`, not secrets in process arguments). Store tool versions and dump results. Do not emit connection strings or archive contents into ordinary logs.
3. Local storage: snapshot/copy the exact private upload volume after writes stop, preserving permissions. Database metadata alone does not recover file bytes. For S3 selection use an approved bucket versioning/backup policy and a snapshot/export that preserves the exact committed key/version references required by media records; a command or API receipt alone is insufficient coverage. The reference supplies no automatic S3 backup adapter.
4. Restore to a separately named isolated database and upload volume/bucket, never over live state. PostgreSQL uses native `pg_restore` into the empty isolated target. Restore local bytes with ownership preserved. Supply the isolated connection/storage configuration to the same compatible app image, with external outbound email/push actions disabled or explicitly isolated. Do not reuse production provider credentials to fabricate delivery evidence.
5. Run actual authorized login/account/session/note/media reads and checksum/known-byte assertions from the isolated restore, compare counts/IDs and schema history, test private access denials and record sanitized results. Assess active refresh/action/secret validity and any external provider state explicitly; a dump exit code cannot prove consistency or recoverability. Only then record backup acceptance. Resume original writers through native lifecycle when their state is verified; preserve the isolated target until review according to its retention policy.

Do not promise schema rollback, transparent cross-database/provider conversion, replica failover, restore completeness or exactly-once migrations without those tests. Routine redeploy never deletes volumes, rotates private values or drops databases. After a timeout discover the original native resources/outcome before repeating an operator action.

## Maintenance ownership and pending evidence

This reference source is developer-owned, including its copied security-sensitive admission/redaction code. Updating a future VCLI binary cannot patch this app. Runtime dependency fixes require an explicit reviewed package/lockfile update plus affected contracts and deployment. Future managed regeneration may update only provenance-tracked composition/config/docs after content preconditions; this hand-built app has no generator provenance claiming that authority. Customized source needs a reviewed manual patch or a narrowly supported codemod, never arbitrary overwriting. The owner assigns the runtime/copied-source patch maintainer before production use. There is no released upgrade engine, advisory inventory of arbitrary custom code, package publication or supported source/data migration implied by this example. All proposed VCLI maintenance/deploy/diagnostics commands remain planned.
