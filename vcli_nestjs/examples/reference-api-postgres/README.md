# VCLI PostgreSQL reference API

A hand-built, executable example of the NestJS output proposed for VCLI. Review and edit this application before implementing the generator. VCLI does not exist yet; this app was not generated by it and does not certify any CLI phase.

## Run the local demo

Use the pinned Node 26 toolchain and npm 11. The reference uses npm because that executable is already available on the contributor host; the future CLI's package-manager baseline remains a separate recorded decision.

```sh
npm ci --ignore-scripts --no-audit --no-fund
# Set DATABASE_URL privately to a dedicated local PostgreSQL database.
# No database selector is accepted by this application.
make build
make migrate
make demo
```

Open `http://127.0.0.1:3101/reference` for the review workbench or `/docs` for OpenAPI. The demo launcher registers a disposable review fixture and confirms its one-use action through private in-process capture, or reuses a successful fixture login on restart. The prefilled browser sign-in uses that fixture. This simulates email receipt and does not establish actual address ownership or mail delivery. No action-token debug endpoint is exposed.

This standalone application uses PostgreSQL/Drizzle + pg only. Supply `DATABASE_URL` and initialize all four schema owners with `make migrate` before starting it. `DATABASE_DRIVER` is rejected; database choice happened when this project was created. Local authentication, private local storage, Socket.IO and captured mail are the development defaults. `npm start` runs the ordinary unseeded application; the demo adds only the explicit disposable fixture and refuses production. It never resets retained data.

For normal development use `make dev`. To select a private configuration file explicitly, use `APP_ENV_FILE=.env.development make dev`. Example files contain configuration names and safe placeholders; creating a private file is a deliberate setup step. Runtime environment variables override the selected file. Staging uses the production runtime with isolated services/secrets.

## Selectable capabilities

| Family         | Reference profiles                                                                  | Evidence boundary                                                                         |
| -------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Persistence    | PostgreSQL/Drizzle + pg only                                                        | Real PostgreSQL, HTTP/protocol and browser/restart checks passed; see verification        |
| Authentication | Firebase ID tokens or local email/password and JWT                                  | Firebase email/password, phone, Google and Apple need actual configured clients/providers |
| Sessions       | Application-owned accounts, installations and revocable sessions                    | Independent of Firebase token refresh                                                     |
| HTTP           | Validated Nest controllers, safe errors, health, OpenAPI and notes example          | Real HTTP assertions establish exercised behavior only                                    |
| Realtime       | Socket.IO, native WebSocket and Centrifugo                                          | Different client protocols and explicit single-instance/cluster guarantees                |
| Media          | Private local files and S3 API adapters                                             | Provider-specific upload/integrity/immutability modes require conformance                 |
| Mail           | Bounded development capture or SMTP                                                 | Capture, SMTP acceptance and inbox delivery are separate outcomes                         |
| Push           | FCM and purpose-routed APNs                                                         | Configured provider acceptance and physical-device delivery remain separate               |
| Diagnostics    | Structured events, retained bounded evidence, read-only MCP, Vector/Logdy artifacts | Same-user readers are not a sandbox                                                       |
| Deployment     | Dokploy, Coolify and CapRover reference artifacts                                   | Files and runbooks do not constitute deployment/operator acceptance                       |

Features use flat NestJS modules and directly injectable services. Shared repositories provide common database operations; focused implementation services handle provider differences. The database is fixed to PostgreSQL, with native SQL conditions and owner-defined tables. See the [expanded repository contract](docs/base-repository.md) for methods, typed projections, batch behavior, row locks, aggregation/joins and bounded iteration. Local and S3 objects retain their storage reference; changing a default does not migrate existing objects or data.

## Review the code

Start with the [code walkthrough](docs/CODE-WALKTHROUGH.md), [actual file tree](docs/PROJECT-TREE.md), [application architecture](docs/architecture.md), [verification results](docs/VERIFICATION.md) and [browser screenshot](docs/assets/reference-workbench.png). The [worker prompt index](docs/agent-prompts/README.md) preserves historical briefs, superseded by the current native database contract.

- `src/core/`: shared configuration, database repositories/transactions, authentication facts and HTTP validation/errors.
- `src/core/logging/`: shared injectable Pino logger, safe structured events and async request/operation correlation; retained JSONL feeds Vector/Logdy and the read-only reader independently.
- `src/modules/accounts`, `identity`, `installations`, `sessions`: separate identity ownership.
- `src/modules/media`, `storage`, `mail`, `push`, `realtime`, `diagnostics`: directly injectable capability services.
- `src/modules/notes`: small authenticated create/read example using owner-private persistence and advisory realtime publication.
- `src/app.custom.module.ts`: developer-owned integration point.
- `src/generated/vcli-app.module.ts`: hand-built example of future tool-owned composition.
- `clients/` and `ops/`: client/protocol examples and selected service/deployment artifacts.
- `docs/agent-prompts/`: the exact self-contained build prompts given to Orca workers.

Each data feature uses entity/service/module files, plus controllers and focused helpers when needed. AccountService, InstallationService, SessionService and NotesService inherit shared BaseRepository operations. One class per file and strict types apply. There are no mandatory application/domain/adapters/public directories. `npm run check:architecture` rejects file/type/feature cycles, core-to-feature imports, forwardRef, service locators, global modules and dynamic dependency loading; builds run that check and the selected-database dependency check first.

No generator lock or installed local VCLI is fabricated for this hand-built reference. The eventual generated project will pin the real CLI and record actual generation ownership.

## Commands and configuration

`make help` lists the available application commands. `npm run typecheck` and `npm run typecheck:tests` use noEmit; the latter resolves the compiled-import paths against source without a prior build. Build before runtime tests, which execute the compiled app. Set a dedicated `TEST_DATABASE_URL` to enable the database regressions; fixtures create and remove isolated schemas, never application data. Missing infrastructure produces explicit skips. `make test-e2e` builds its required input itself. Build, checks and runtime assertions remain separately reported outcomes.

For selected local dependencies use `COMPOSE_PROFILES=postgres make services-up` or add the `centrifugo` or `diagnostics` profile. Native Compose accepts a colon-separated `COMPOSE_FILE` list when a contributor-local override is needed. Check the host's resource/download policy and [operations setup](docs/operations.md) before starting containers; no profile is chosen automatically. Ordinary `make services-down` preserves volumes.

`make start-prod` starts a compiled app with validated production configuration; it does not provision, migrate or deploy services. Production refuses captured mail. Schema migration is an explicit release step.

Read [identity](docs/identity.md), [storage](docs/storage.md), [delivery](docs/delivery.md), [realtime](docs/realtime.md) and [operations](docs/operations.md) for exact interfaces and setup. See [verification](docs/VERIFICATION.md) for the actual tested source, commands, evidence levels and pending external checks.

## Current scope

The owner selected a working local demo with external verification pending. No provider credentials are copied or invented. No npm publication, production migration, provisioning or live deployment is part of this work. The wider VCLI phase requirements remain tracked in the repository's phase board; this reference is an editing surface, not a claim that the entire product has been implemented.

The current runtime is single-instance, uses mediated storage transfers, and creates fresh installation bindings per login. Presigned/multipart/custom-S3 modes, stable installation reuse/rebind, linking/deletion and application-delivered Firebase action links remain unsupported or unfinished as listed in [verification](docs/VERIFICATION.md). Their absence is visible for this review and does not remove them from the product plan.
