# Installation-bound push

Apply the generated schema release command before startup. Push keeps a bounded owner aggregate (1024 destinations globally, 32 per account): MongoDB compare-and-swap revision or PostgreSQL row-lock transaction serializes uniqueness, replacement and exact cleanup. No external provider I/O occurs inside these callbacks. Initialization creates the selected store; it does not copy provider secrets or make a provider/device acceptance claim.

`PUSH_ENVIRONMENT=sandbox|production` is explicit and independent of `NODE_ENV`. Application origin, selected provider project/topic and APNs environment identify scope. Changing scope requires client re-registration. APNs production must equal the push environment; sandbox tokens never route to production. For selected provider setup see the corresponding generated checklist.

Authenticated registration derives account, installation and binding generation from verified session authority. A caller-supplied installation ID or token proves no ownership. Register after login/rebind/possession recovery and token refresh. Registration rotates the secret token generation and preserves the destination ID within an unchanged binding/purpose. Rebinding advances installation generation; prior generations and revoked/expired sessions are ineligible. Multiple valid sessions on one installation may share authority, but each destination is tied to the registering session: revoke/logout of that session fences its destination; a still-valid sibling must re-register. List and revoke return only the current installation's safe summaries. Revoke using the exact token generation before voluntary logout when possible. No raw token/hash/account/session secret appears in those summaries.

Existing rows without installation generation or explicit environment decode as generation zero and never send. There is no inference or automatic preserving-owner migration. Have the authenticated client re-register to replace those rows; legacy rows on other installations remain reserved until an operator explicitly removes them after ownership review. Back up the restricted destination aggregate according to the application's secret handling policy. Never rewrite generation zero from whatever account currently owns an installation.

Internal `PushService.notifyAccount` / `notifyInstallation` accepts UUID operationId, purpose, small opaque data references and expiry <= five minutes. Concurrency is four operations, serial per destination, at most 32 destinations and three provider attempts. Retry waits are 1s then 2s; longer provider Retry-After is returned as unavailable without sleeping or scheduling. A wait that crosses expiry is refused. `unknown` means possible provider acceptance and never retries automatically. The Firebase Admin SDK can internally retry certain transport failures; operation identity does not establish provider deduplication. There is no queue, restart recovery, durable retry or exactly-once guarantee.

Immediately before disclosure, the service rechecks exact persisted destination and current session account/installation/generation/expiry. A concurrent change after the last check or while an SDK call is in flight cannot recall bytes or a provider-accepted push. Keep payloads free of confidential content; fetch current data through authenticated application APIs. A delayed invalid-token result rechecks authority and removes only the exact account/installation/binding/token generation. Payload, credentials, connectivity and unknown errors never prune a destination. Raw SDK errors are reduced to fixed safe codes.

Purpose routing is explicit: ordinary uses one selected provider (FCM wins when both selected); background and VoIP use direct APNs only. The public self-check endpoint accepts ordinary/background, never VoIP. No arbitrary HTTP callId enables a VoIP wake. Application composition must pass a `TrustedCallInvitationPolicy` to `createPushRuntime(config,authority,{voipPolicy})` for programmatic delivery. Its `authorize` method must read application-owned current call facts, recipient membership, invitation state and expiry; it is invoked again on every destination attempt. Default policy is unconfigured and refuses delivery. Compose that policy above call and push owners; never introduce a calls/push dependency cycle or import raw foreign models.

Provider acceptance does not prove OS presentation, user receipt, CallKit acceptance or native setup. Real credentials, project/topic/environment and physical Android/iOS lifecycle acceptance remain external checks.
